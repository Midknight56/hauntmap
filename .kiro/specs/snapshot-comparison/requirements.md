# Requirements Document

## Introduction

`snapshot-comparison` is the before/after feature of HauntMap: two analyzed snapshots of one project (the bundled `manor/before` and `manor/after` pair, or the current investigation and the live snapshot Kiro produced; two folders or refs chosen by the user are not compared in this build) are compared by structural relation ID in `src/analysis/graph/compare.ts`, laid out once on their union so common rooms keep their coordinates, drawn with three change states (amber lamp, ghost outline, green doorway) that each have a text equivalent. It serves the developer reviewing a small refactor and the judge who watches a dependency loop's corridor close when the import that completed it is removed. It implements "Compare revisions", the comparison rows of "Intended competition experience", the comparison part of "Storage and privacy", work package H5 and matrix rows 16, 23 and 24 (plus this spec's share of row 28) of `plans/hauntmap-implementation-plan.md` (revision 3, 2026-11-03), on top of the `Investigation`, `CycleReport` and `ComparisonResult` contracts of that plan and the `compare` slot and handoff, `applyLayout`, `replaceInvestigation`, `setLayoutRequestBuilder` and legend provider of the `investigation-ui` spec. The export parts of rows 11, 25 and 27 are not built. Owner: Kiro, alone in the main checkout, under `.kiro/steering/revision-2026-11-16.md`: tasks 1a to 4b, 8 to 12, 14 and 15 are done; tasks 5, 6, 7 and 13 (the export feature) are not done; the `intake` spec is not built and nothing here depends on it. `kiro-integration` task 11 waits for this spec's task 10 (`registerCompare` on `main`). Four changes in files of `investigation-ui` are needed and are gated on an exception in `.kiro/steering/ownership.md` (gates G1 to G4 in `tasks.md`).

Terms used below. **Snapshot**: one `Investigation` (`schemaVersion: 1`) plus its label and an optional in-memory source map. **Earlier** and **newer** snapshot: the `before` and `after` sides of a comparison; the UI words are `Earlier` and `Newer`, the contract fields are `before` and `after`. **Module ID**: `ModuleRecord.id`, a path relative to its own snapshot's root with forward slashes and no leading `./`. **Relation ID**: `ImportRecord.relationId`, `JSON.stringify([from, targetKey, syntaxKind, dependencyKind])`; **occurrence ID**: `ImportRecord.occurrenceId`, `JSON.stringify([from, line, column, specifier])`. **Union**: the module and relation sets of both snapshots together. **Shown snapshot**: the side whose `Investigation` currently sits in the fleet store (`ViewState.investigation`) and feeds the inspector, evidence trail, Evidence view and panels. **Drawn relation**: a relation with `resolution: "local"` that is in the active preset, one per relation ID (the fleet's `LayoutRequest.relations`); it always counts in its wing corridor, and it becomes a **door** only when its importer and target rooms are both drawn. **Ghost**: a room or door that exists only in the earlier snapshot. **Status region**: the one `role="status"` element written through `store.actions.setStatus`. **Fleet store**: `src/features/investigation/store.ts`; **registry**: `src/features/investigation/registry.ts`; **named laptop**: a machine the owner names in `docs/performance.md`; no row exists, so every figure that needs it is a target left for the owner. Fixture hashes below are SHA-256 hex values of the fixture texts listed in `design.md`, computed on November 3, 2026.

## Requirements

### Requirement 1 — Two analyzed snapshots

**User Story:** As a developer reviewing a small refactor, I want to compare the investigation on screen with a newer snapshot of the same project — the bundled revised manor or the snapshot Kiro just produced — so that both sides of the comparison are computed from real source and never from a precomputed animation.

#### Acceptance Criteria

1. WHEN the `Compare revisions` control (registered in the `compare` toolbar slot, a button with `aria-expanded`) is activated THEN THE SYSTEM SHALL open the panel `Compare revisions` (`<section role="region" aria-labelledby>` its heading) with the sentence `Compare <current sourceLabel> with a newer snapshot.` and exactly one of these buttons: `Revised manor sample` (rendered only while `sourceLabel` is `manor/before`) or `Bundled manor pair` (rendered otherwise, followed by the sentence `Replaces the current investigation with manor/before and compares it with manor/after.`); the panel has no button for a local folder or a GitHub repository.
2. WHEN `Revised manor sample` is activated THEN THE SYSTEM SHALL call `loadSample("manor/after", base)` (one request to `demo/manor/after/sources.json` relative to the app base), run the analysis worker on the returned `SourceSet` through `analysisClient.analyze({ files, rootLabel, options }, onProgress?)` with `options` equal to the earlier investigation's `options` (so that `optionsDiffer` is empty; the preset selected in the toolbar is a view setting, not an analysis option, and never enters), and compare the current investigation (earlier) with the analyzed result (newer) by calling `compareInvestigations` at run time; THE SYSTEM SHALL fetch no precomputed comparison, layout or animation file (`tests/compare/e2e/compare.spec.ts` records every request after the sample request and asserts none).
3. WHEN `Bundled manor pair` is activated THEN THE SYSTEM SHALL load and analyze `manor/before` as `investigation-ui` 1.3 does (`loadSample`, the analysis client, the source map built from the sample's files), open it with `openInvestigation(investigation, sourceText, { expandWing: "src/orders", demo: false })` (which lays it out and replaces the current investigation), wait for `layoutStatus` to become `idle` (IF it becomes `failed` THEN stop there: the fleet's 3.7 message stays, `manor/before` stays open and the comparison stays idle), and then proceed exactly as 1.2.
4. WHEN the `compare` handoff is called with `{ before, after, layoutKey }` (by the steps panel with `after: { sample: "manor/after" }`, or by the `Open live snapshot` control with an `Investigation` whose `sourceLabel` starts with `live:`) THEN THE SYSTEM SHALL take `before` as the earlier snapshot without re-analyzing it (its source map is `ViewState.sourceText` when `args.before` is the investigation in the fleet store, otherwise `null`), acquire `after` as in 1.2 when it is a sample reference and otherwise use the given `Investigation` with `sourceText: null`, and resolve the returned promise when the comparison is active (6.1); IF the comparison fails THEN THE SYSTEM SHALL show the message of Requirement 10 first and then reject the promise with an `Error` carrying that message.
5. Withdrawn under the revision of 16 November 2026. Comparison of a local folder or a GitHub repository chosen by the user is not built: the panel has no such button, no `intake` handoff is called, no flag guards it and nothing in this spec depends on the `intake` spec.
6. THE SYSTEM SHALL name snapshots by their `sourceLabel` (`manor/before`, `manor/after`, `live:samples/manor`) in the panel, the status region, the legend annotations and the export; a label is rendered as text and never parsed for meaning.
7. WHILE a newer snapshot is being acquired or analyzed THE SYSTEM SHALL show `Comparing <earlier label> with <newer label>…` in the status region (the newer label is `manor/after` or `live:…` as soon as it is known, otherwise `the newer snapshot`), keep `ViewState.investigation`, `selection`, `routeFilter`, `camera`, `expandedWings` and `layout` unchanged, render the panel's button `aria-disabled="true"`, and ignore a second activation.
8. THE SYSTEM SHALL hold both snapshots and both source maps in memory only (`src/features/compare/store.ts`), never in `localStorage`, `sessionStorage` or IndexedDB; WHEN `End comparison` (6.6) or `Restart demo` (6.7) runs THEN THE SYSTEM SHALL drop the newer snapshot and its source map so that the comparison store holds no `Investigation` afterwards.

### Requirement 2 — Comparable identity across roots

**User Story:** As a developer comparing two checkouts in different folders or two refs of one repository, I want modules matched by root-relative path and relations by structural ID, so that folder names, ref names and statement positions never appear as differences.

#### Acceptance Criteria

1. THE SYSTEM SHALL match modules across snapshots by `ModuleRecord.id` and relations by `ImportRecord.relationId` only; `sourceLabel`, the root folder name, the ref, `occurrenceId`, `line` and `column` SHALL play no part in matching (`tests/compare/identity.test.ts`: the `identical` fixture, the same investigation under the labels `local:manor-before` and `local:manor-after`, yields empty `addedModules`, `removedModules`, `changedModules`, `addedRelations` and `removedRelations`).
2. IF either snapshot has `schemaVersion` other than `1` THEN `compareInvestigations` SHALL return `{ ok: false, error: { code: "incompatible-schema", message: "schema version <v> is not 1" } }`; IF either has `resolverMode` other than `"documented-source-subset"` THEN `{ ok: false, error: { code: "incompatible-resolver", message: "resolver mode \"<m>\" is not \"documented-source-subset\"" } }`; THE SYSTEM SHALL then show `The snapshots cannot be compared: <message>. The current investigation is unchanged.` in the status region.
3. IF `before.options` and `after.options` differ in any field (deep comparison, field by field) THEN THE SYSTEM SHALL list the differing field names in `ComparisonDetail.optionsDiffer` and the panel SHALL show `The snapshots were analyzed with different options (<field>, <field>); some differences may come from the options.` under `Notes`; the comparison SHALL still run (`options-mismatch` fixture: `optionsDiffer` equals `["includeExtensions"]`).
4. IF a module exists in both snapshots with `parseStatus: "failed"` in exactly one of them THEN the panel SHALL show under `Notes` `<id> could not be parsed in the <earlier|newer> snapshot; its relations there are unknown and appear as <added|removed>.` (failed in the earlier snapshot → `appear as added`; failed in the newer → `appear as removed`).
5. WHEN the two snapshots have the same module IDs, the same relation IDs and equal hashes for every module THEN THE SYSTEM SHALL still activate the comparison and show `No differences: the snapshots have the same modules, relations and source hashes.` in the panel and in the status region.
6. THE SYSTEM SHALL compare `sourceHash` values as opaque strings produced by `analysis-core` (SHA-256 hex of the UTF-8 text) and SHALL never read or hash source text in `compare.ts`; `tests/compare/boundary.test.ts` fails if `src/analysis/graph/compare.ts` imports anything other than `src/contracts/**` and sibling files of `src/analysis/graph/`, and `tests/analysis-boundary.test.ts` (analysis-core) keeps it free of DOM, `src/scene`, `src/features` and `src/components` imports.

### Requirement 3 — Structural comparison by relation ID

**User Story:** As a developer, I want the comparison to report exactly which import relations were added or removed and which files changed, by structural identity rather than statement position, so that moving a line, inserting a comment or deleting a duplicate import statement never looks like a dependency change.

#### Acceptance Criteria

1. THE SYSTEM SHALL compute the plan's `ComparisonResult` as follows: `addedModules` = IDs in the newer snapshot and not in the earlier; `removedModules` = IDs in the earlier and not in the newer; `changedModules` = IDs in both whose `sourceHash` values differ; `addedRelations` = one `RelationRef` per distinct `relationId` present among the newer snapshot's `imports` and absent from the earlier's, over every relation regardless of `resolution` or preset; `removedRelations` the mirror; `before.relationCount` and `after.relationCount` = the number of distinct relation IDs in that snapshot; `before.moduleCount` and `after.moduleCount` = `modules.length`; `cyclicComponentsBefore` and `cyclicComponentsAfter` = `components.length` of the cycle report of that snapshot under `static-value`; `before.label` and `after.label` = the snapshots' `sourceLabel` values; `preset: "static-value"`; `schemaVersion: 1`.
2. THE SYSTEM SHALL sort `addedModules`, `removedModules` and `changedModules` in UTF-16 code-unit order and `addedRelations` and `removedRelations` by `relationId` in the same order (the comparator `(a, b) => (a < b ? -1 : a > b ? 1 : 0)`, never `localeCompare`), and SHALL return deep-equal results when the `modules` or `imports` arrays of either input are permuted (`tests/compare/compare.test.ts` shuffles both; P6).
3. THE SYSTEM SHALL fill each `RelationRef` from the first occurrence of its relation ID (lowest `line`, then lowest `column`) in the snapshot where the relation exists, copying `relationId`, `from`, `to`, `specifier`, `syntaxKind`, `dependencyKind` and `resolution` unchanged; a boundary relation keeps `to: null` and its original specifier (`boundary-change` fixture: `removedRelations` is exactly `[{ from: "src/app.ts", to: null, specifier: "./ghosts/missing", syntaxKind: "import", dependencyKind: "value", resolution: "unresolved", relationId: JSON.stringify(["src/app.ts", ["unresolved", "./ghosts/missing"], "import", "value"]) }]`).
4. WHEN the `comment-shift` fixture pair is compared (earlier `src/a.ts` is `import { b } from "./b";` at line 1, hash `ebf78fc7fae8b7f83c2ffd57b69b2f89f5321c3dd0713dd04544462720f9d6b0`; newer `src/a.ts` has the same statement at line 3 under two comment lines, hash `f6991c23841a2ae5b79ca756c263379ffc9245d5abb40018d04d6674e5718058`) THEN `changedModules` SHALL equal `["src/a.ts"]`, `addedRelations` and `removedRelations` SHALL be empty, and the relation's `occurrenceId` SHALL differ between the snapshots while its `relationId` is equal (matrix row 23).
5. WHEN the `duplicate-occurrence` fixture pair is compared (earlier `src/a.ts` has `import { x } from "./b";` at line 1 and `import { y } from "./b";` at line 2, hash `ed01911bf39910668204a57f39e0d5e6dbccdcd247be34668096769551e3ccce`; newer keeps only line 1, hash `1ce2854c1718177a79b04336be4fc29bb52fa860d5ed92a6842a2e4995c009de`) THEN `removedRelations` SHALL be empty, `changedModules` SHALL equal `["src/a.ts"]`, and `ComparisonDetail.occurrenceCounts["src/a.ts"]` SHALL equal `{ before: 2, after: 1 }` (matrix row 24).
6. WHEN `public/demo/manor/before` and `public/demo/manor/after` are loaded with the plan's default `AnalysisOptions`, analyzed by the analysis module and compared THEN the result SHALL have exactly one removed relation with `from: "src/notifications/receipt.ts"` and `to: "src/orders/checkout.ts"`, exactly one added relation with `from: "src/notifications/receipt.ts"` and `to: "src/orders/summary.ts"`, `changedModules` equal to `["src/notifications/receipt.ts", "src/orders/checkout.ts"]`, empty `addedModules` and `removedModules`, `before.moduleCount` and `after.moduleCount` equal to 40, `cyclicComponentsBefore` equal to 1 and `cyclicComponentsAfter` equal to 0 (matrix row 16); the two relations' `syntaxKind`, `dependencyKind`, `specifier` and the two `relationCount` values are read from `tests/compare/fixtures/manor-pair/expected.json`, authored by hand from the sample sources (read on 2026-11-16: `relationCount` 72 and 72, because each of the two `expected.json` files lists 72 imports with no repeated relation ID; occurrence counts `src/notifications/receipt.ts` 4 → 4 and `src/orders/checkout.ts` 6 → 6; the removed relation's specifier `../orders/checkout`, the added one's `../orders/summary`, both `import`, `value`, `local`).
7. WHEN the `rename` fixture pair is compared (earlier `src/util/format.ts`, newer `src/util/formatMoney.ts`, both with hash `40483aaf98549a7d523cf046595dfa937b38a931996d5e3ad3f37c110f698df7`; `src/app.ts` imports `./util/format` in the earlier snapshot and `./util/formatMoney` in the newer) THEN `removedModules` SHALL equal `["src/util/format.ts"]`, `addedModules` `["src/util/formatMoney.ts"]`, `removedRelations` the single relation `src/app.ts → src/util/format.ts`, `addedRelations` the single relation `src/app.ts → src/util/formatMoney.ts` and `changedModules` `["src/app.ts"]`; THE SYSTEM SHALL not pair, link, colour or label the two modules as a rename anywhere, and the panel SHALL show `Renames are shown as a removal and an addition; HauntMap does not infer renames.`
8. WHEN the `cycle-closes` fixture pair is compared (earlier `src/x.ts` imports `./y` and `src/y.ts` imports `./x`; newer without the `y → x` import) THEN `cyclicComponentsBefore` SHALL be 1, `cyclicComponentsAfter` 0 and `removedRelations` exactly the `src/y.ts → src/x.ts` relation.
9. THE SYSTEM SHALL compute `compareInvestigations` for two generated investigations of 1,000 modules and 3,000 relations each within 500 ms on the named laptop (a target until recorded): `tests/compare/compare.test.ts` times it with `performance.now()`, prints the figure on every run, asserts a regression ceiling of 5,000 ms on every run, and asserts the 500 ms target only when the environment variable `HAUNTMAP_PERF_DEVICE` is set (the owner's run on the named laptop); the figure goes in the task 2 and task 15 log rows marked as not recorded on the named laptop, and this spec writes no row in `docs/performance.md` (claims policy: performance statements need a recorded check on named hardware).

### Requirement 4 — Union layout computed once, positions preserved

**User Story:** As a judge watching the comparison, I want every room that exists in both snapshots to stay exactly where it was, so that the only movement on screen is the change itself.

#### Acceptance Criteria

1. WHEN a comparison becomes active AND the fleet store holds a `LayoutResult` with `layoutStatus: "idle"` whose `layoutKey` equals the `layoutKey` passed to the handoff (for the panel buttons: the current `state.layout.layoutKey`) THEN THE SYSTEM SHALL build the union layout with `extendLayout(current, union, request, place, layoutKey)` (pure and synchronous, `src/features/compare/unionLayout.ts`): every `WingBox`, `RoomBox` and `GroupedRoomBox` of the current layout keeps its `x`, `y`, `w` and `h`; rooms are added only for modules present only in the newer snapshot; rooms of modules present in neither snapshot (left over from a replaced newer snapshot, 6.8) are dropped; the result is applied with `store.actions.applyLayout`.
2. WHEN a module exists only in the newer snapshot THEN THE SYSTEM SHALL place its room as follows: wing expanded and showing fewer than 80 rooms → the next slot of a new row below the wing's lowest room (`x = wing.x + 24 + k × 112` for `k = 0, 1, …` while `x + 96 ≤ wing.x + wing.w − 24`, `y = lowest room bottom + 16`, then the next row), growing the wing box downward so that `wing.y + wing.h` is at least the bottom of the new row plus 24 (80 units per new row when the wing's bottom padding was the fleet's 24), added rooms filling a new row left to right in module-ID order and a new row starting only when the previous new row is full; wing expanded and showing 80 rooms → `hiddenCount + 1` and the grouped room's label `+<n> more modules`; wing collapsed → `moduleCount + 1`; wing absent → a new collapsed `WingBox` of 144 × 120 at `x = bounds.x + bounds.w + 48`, `y = bounds.y + 32` (each further new wing 48 units below the previous one) with `rank = max rank + 1`, `expanded: false`.
3. IF a grown wing box intersects another wing box THEN THE SYSTEM SHALL resolve it with one deterministic pass: process the grown wings in ascending `rank` order (ties by wing name in code-unit order); for each grown wing, translate downward by its growth amount every wing whose top edge is at or below the grown wing's original bottom edge and whose horizontal extent overlaps the grown wing's, together with that wing's rooms and grouped room; a wing translated by several grown wings accumulates the translations (it may move more than once); after the single pass over the grown wings, `tests/compare/union-layout.test.ts` asserts that no two wing boxes intersect; THE SYSTEM SHALL show `<n> rooms moved to make room for <k> added modules.` appended to the ready message of 6.1 (the status region holds one message) and no other room SHALL move (P9).
4. THE SYSTEM SHALL recompute doors, sealed doorways and corridors over the union: one `DoorBox` per drawn relation ID of either snapshot whose two rooms are drawn, placed with the fleet's placement rule exported by `src/scene/layout/doorsPlacement.ts` (*verify* its export name); one `SealedBox` per boundary relation ID of either snapshot whose importer room is drawn; one `CorridorBox` per ordered wing pair counting the distinct drawn relation IDs of the union; `bounds` the union of wing boxes plus 32 units; `layoutKey` the SHA-256 hex of the canonical JSON `{ base: <current layoutKey or null>, modules: <sorted union IDs>, relations: <sorted union drawn relation IDs>, expandedWings: <sorted>, preset, engine: { name, version } }`.
5. IF no current `LayoutResult` exists, its `layoutKey` differs from the handoff's, or `layoutStatus` is not `idle` THEN THE SYSTEM SHALL install the union builder and call `retryLayout()`, so that the fleet store sends one union `LayoutRequest` (union `modules`, `relations` and `boundaries`, the current `expandedWings` and preset) through its own layout client with its revision guard, 10,000 ms timeout and `Retry layout` handling unchanged, and the comparison continues when `layoutStatus` is `idle` or `failed` (10.5); the sentence `The map was laid out again for the comparison; rooms may have moved.` is appended to the ready message of 6.1. The builder receives only `ViewState`, so the fleet's `bring` swap of a module beyond the 80 shown is not available while a comparison is active: a newly expanded wing shows its 80 lexically smallest modules, and a wing already expanded keeps its `shownIds`.
6. WHILE a comparison is active THE SYSTEM SHALL keep the union request builder installed on the fleet store (`store.actions.setLayoutRequestBuilder(unionBuilder)`) so that `expandWing`, `collapseWing`, `setPreset` and `retryLayout` each send exactly one union request and never a request built from one snapshot; WHEN the comparison ends THEN THE SYSTEM SHALL remove the builder (`setLayoutRequestBuilder(null)`) and send one ordinary layout request through `retryLayout()`.
7. WHEN the shown snapshot is toggled (6.2) THEN THE SYSTEM SHALL send no layout request and SHALL not call `SceneHandle.setLayout`; the `LayoutResult` in the store SHALL be the same object before and after the toggle (`tests/compare/toggle.test.ts` with the fake scene counts zero `setLayout` calls and zero layout requests over 20 toggles).
8. WHEN the manor pair comparison starts from the manor demo with every wing expanded first (through the development hook, so that all 40 rooms are drawn; a collapsed wing draws no rooms, `investigation-ui` I3) THEN every one of the 40 rooms and every wing SHALL report the same `screenRectOf` rectangle before the comparison and while either side is shown (`tests/compare/e2e/compare.spec.ts` reads every room ID's and every wing's rectangle three times; a `null` rectangle fails the test); a second case keeps only `src/orders` expanded (the demo's opening state) and asserts the same for its drawn rooms and every wing rectangle; in both cases only the doors on `src/notifications/receipt.ts` may change position, and no status message about moved rooms SHALL appear.
9. THE SYSTEM SHALL complete `extendLayout` for a union of 1,000 modules and 3,000 drawn relations within 100 ms on the named laptop (a target until recorded): `tests/compare/union-layout.test.ts` times it, prints the figure on every run, asserts a regression ceiling of 1,000 ms on every run, and asserts the 100 ms target only when `HAUNTMAP_PERF_DEVICE` is set; the figure goes in the task 3 and task 15 log rows, marked as not recorded on the named laptop.

### Requirement 5 — Change states with text equivalents

**User Story:** As a developer, I want each changed element drawn with exactly one marker whose meaning is also stated in words, so that a colour-blind user, a screen-reader user and the exported report receive the same facts as the illustration.

#### Acceptance Criteria

1. WHILE the newer snapshot is shown THE SYSTEM SHALL draw: a room of a module in `changedModules` in the `comparison-changed` state (an amber lamp glyph on the room's north edge, state label `changed`); a room in `removedModules` and a door of a relation in `removedRelations` in the `comparison-removed` state (ghost outline: a 2-unit dashed outline in `--removed`, no fill, label text at `--room-subdued-ink`, state label `removed`); a door of a relation in `addedRelations` in the `comparison-added` state (green doorway: fill `--added`, glyph `+`, state label `added`); a room in `addedModules` in the `comparison-added` state (2-unit outline in `--added`, glyph `+`, state label `added`); every other element in the state the fleet scene would give it.
2. WHILE the earlier snapshot is shown THE SYSTEM SHALL draw rooms and doors of the earlier snapshot in their ordinary states, rooms in `changedModules` in `comparison-changed`, and SHALL not draw rooms or doors that exist only in the newer snapshot (their layout slots stay empty so that no room moves on toggle, and the scene does not hit-test them while they are hidden).
3. THE SYSTEM SHALL register, through `registry.registerLegendEntries`, a provider that returns `[{ concept: "Changed source", costume: "amber lamp" }, { concept: "Removed in the newer snapshot", costume: "ghost outline" }, { concept: "Added in the newer snapshot", costume: "green doorway" }]` while a comparison is active and `[]` otherwise (fleet 5.1 appends them as `Changed source — amber lamp`, `Removed in the newer snapshot — ghost outline`, `Added in the newer snapshot — green doorway`).
4. THE SYSTEM SHALL define the three states in `STATE_STYLES` of `src/scene/styles.ts` (completing the three `comparison-*` entries that `investigation-ui` created; the file is the fleet's and is changed under gate G3 of `tasks.md`) each with a non-colour companion (lamp glyph, dashed outline, `+` glyph) and add the tokens `changed: "#f0b429"`, `removed: "#9a93a8"`, `added: "#5ad48a"` to `TOKENS` and `src/styles/tokens.css`; `tests/compare/styles.test.ts` SHALL compute the WCAG contrast ratio of each of the three tokens against `floor` and against `room` with the relative-luminance formula and fail below 3:1, and SHALL fail if any of the three states differs from `default` only in colour.
5. THE SYSTEM SHALL provide a text equivalent for every drawn marker in the Comparison panel (Requirement 7): every item of the five lists and every `Selected change` card states the change in words (`Removed in <newer label>`, `Added in <newer label>`, `Only in <label>`, the two hashes); the tooltips and the inspector keep the fleet's own lines, because the fleet registry has no annotation method, and no annotation provider is built.
6. THE SYSTEM SHALL keep a ghost room's and a ghost door's hit targets intact (their boxes stay in the union layout, so the fleet's `buildHitTargets` includes them) so that both are selectable by pointer with the fleet's priority unchanged, and SHALL list both as buttons in the panel (7.2).
7. THE SYSTEM SHALL never mark a module as changed when its hash is equal, whatever happened to its relations, and never mark a relation as removed or added because a file hash changed: on the `comment-shift` and `duplicate-occurrence` fixtures the room `src/a.ts` is in `comparison-changed` and the door `src/a.ts → src/b.ts` is in its ordinary state (`tests/compare/comparison-states.test.ts` on `comparisonStateOf`).
8. THE SYSTEM SHALL use the same three states, glyphs and tokens for a comparison whose newer snapshot is a live snapshot (`live:` label, no source map) as for any other; `comparisonStateOf` SHALL ignore labels (P10).
9. THE SYSTEM SHALL describe changes only with the words `removed`, `added`, `changed`, `imports`, `only in`; `tests/compare/vocabulary.test.ts` fails if `broken`, `breaks`, `fails`, `dead`, `unused`, `unreachable`, `safe`, `risk` or `rename detected` appears (whole words, case-insensitive) in `src/features/compare/**` or `src/scene/compare/**`.

### Requirement 6 — Earlier/Newer toggle and the closing corridor

**User Story:** As a judge, I want to flip between the earlier and the newer snapshot in place and watch a dependency loop's corridor close when the import that completed it is removed, so that the visual change on screen is exactly the verified graph change.

#### Acceptance Criteria

1. WHEN a comparison becomes active THEN THE SYSTEM SHALL show the newer snapshot first (`shown: "after"`), put the newer snapshot's `Investigation` and source map into the fleet store through `store.actions.replaceInvestigation(investigation, sourceText, { keepLayout: true })` (which keeps `layout`, `camera`, `expandedWings`, `preset`, `activeView` and `selection`, drops a `routeFilter` containing an ID absent from the new investigation, and recomputes an open panel; design, request R1), apply the comparison style state to the scene, and show `Comparison ready: <r> removed, <a> added, <c> changed modules; loops <x> → <y>. Showing the newer snapshot.` in the status region, followed, when 4.3 or 4.5 applies, by that sentence.
2. THE SYSTEM SHALL provide in the panel a `role="radiogroup"` labelled `Show` with the options `Earlier (<earlier label>)` and `Newer (<newer label>)` (ArrowLeft/ArrowRight and ArrowUp/ArrowDown move the checked option); WHEN the checked option changes THEN THE SYSTEM SHALL call `replaceInvestigation` with that snapshot, update the comparison style state (5.1, 5.2), keep the camera, and show `Showing the earlier snapshot (<label>).` or `Showing the newer snapshot (<label>).`; the inspector, evidence trail, Evidence view, loops and who-imports panels SHALL operate on the shown snapshot (for the manor pair, `Dependency loops (static-value)` reads `1 loops` while the earlier snapshot is shown and `0 loops` while the newer is shown).
3. WHEN the view switches to the newer snapshot AND the route filter at that moment is a cycle witness AND at least one of its relation IDs is in `removedRelations` THEN THE SYSTEM SHALL play the closing-corridor transition: the violet corridor segments and step numbers fade to nothing over 600 ms while the removed door takes the `comparison-removed` state; no room moves; `scene.debug().activeTweens` returns to 0 within 700 ms of the switch; the route filter is dropped by `replaceInvestigation` and the evidence trail shows the fleet's empty-state sentence.
4. WHILE reduced motion is in effect (fleet 11.5: media query or the `Motion` toggle) THE SYSTEM SHALL apply every comparison state change instantly, creating no tween (`activeTweens` is 0 at every 250 ms sample of `tests/compare/e2e/compare.spec.ts`).

### Requirement 10 — Failure and recovery

**User Story:** As a user, I want every failure during a comparison or an export to leave my investigation, selection and map exactly as they were, with one sentence saying what happened and what to do next, so that trying a comparison is never a risk to the work on screen.

#### Acceptance Criteria

1. IF `loadSample("manor/after")` returns `{ ok: false }` THEN THE SYSTEM SHALL show `The revised manor sample could not be loaded (<status or error name>). The current investigation is unchanged.`, where `<status or error name>` is the first parenthesized text of the `message` that `loadSample` returns (it has no separate status field; `unknown error` when there is none), keep the comparison store `idle`, and leave `ViewState.investigation`, `selection`, `routeFilter`, `camera`, `expandedWings` and `layout` deep-equal to their values before the activation (`tests/compare/e2e/compare.spec.ts` routes `demo/manor/after/sources.json` to HTTP 500 and compares the state through the development hook); on the `Bundled manor pair` path (1.3), where `manor/before` has already replaced the previous investigation, the same failure SHALL leave `manor/before` open with its own layout and the message SHALL end with `manor/before stays open.` instead of `The current investigation is unchanged.`; IF `loadSample("manor/before")` itself fails on that path THEN THE SYSTEM SHALL show the message of `investigation-ui` 1.6 (`The manor sample could not be loaded (<status or error name>). Reload the page.`), and IF the analysis of `manor/before` rejects THEN the message of `investigation-ui` 1.10 (`The manor sample could not be analyzed (<message>). Reload the page.`); in both cases the previous investigation stays open (`tests/compare/store.test.ts` covers both pair-path cases).
2. IF the analysis worker rejects, times out or is terminated while analyzing the newer snapshot THEN THE SYSTEM SHALL show `The newer snapshot could not be analyzed (<message>). The current investigation is unchanged.` with the same preservation; a cancel or supersession during that analysis (the fleet client's terminate-and-recreate) SHALL never replace the earlier investigation.
3. Withdrawn under the revision of 16 November 2026: no `intake` handoff exists, so no intake failure can occur.
4. IF `compareInvestigations` returns `{ ok: false }` THEN THE SYSTEM SHALL show the message of 2.2 with the same preservation.
5. IF the union layout request of 4.5 fails or times out THEN THE SYSTEM SHALL still activate the comparison (lists, toggle, cards and notes work), keep the fleet's 3.7 handling (the Evidence view, `Retry layout`) and append its sentence to the ready message of 6.1, because the status region holds one message: `The map layout did not finish (<reason>). The Evidence view has the full investigation.` with `Retry layout`; WHEN a layout later arrives THEN THE SYSTEM SHALL apply the comparison style state to it.
6. IF the handoff promise of 1.4 rejects THEN the caller's state is the caller's (the steps panel keeps the step `To do`; the live-snapshot control keeps its own view) and THE SYSTEM SHALL not write a second status message after the one of 10.1–10.4.
7. THE SYSTEM SHALL write every failure message through `store.actions.setStatus`, log to the console only the error name and stack, and never log or store a label, path, specifier or hash (no telemetry exists in this build; `tests/compare/store.test.ts` spies on `console.error`).
8. WHEN any failure of 10.1–10.4 occurs THEN THE SYSTEM SHALL keep focus on the control that was activated, keep the panel open, and re-enable its buttons.
