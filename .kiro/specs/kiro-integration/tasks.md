# Implementation Plan

Kiro-owned spec (owner `kiro`; Crew is not used for this spec, so every task carries `_Owner: kiro`). Window: November 4–11 for tasks 1a–8 (package, hooks, registration, steering), November 6–7 for task 13a (the pilot's Crew definitions to `main`), November 15–19 for tasks 9–10 (the `compare` tool, the live control against the registry alone), November 21–22 for task 11 (the browser journey; it needs the `compare` handoff that `snapshot-comparison` task 10 wires into `src/components/App.tsx` on November 19–21), November 22–23 for task 12 (the H9 recorded session, gate November 24), and November 28–December 2 for tasks 13b–15 (`docs/crew.md`, release checks, log and write-up; gate December 2). Dependencies on other specs: task 9 waits for `src/analysis/graph/compare.ts` (`snapshot-comparison` task 2); task 10 waits for the `live-snapshot` slot and the registry (`investigation-ui` tasks 2b and 6a); task 11 waits for `registerCompare` on `main` (`snapshot-comparison` task 10) and for the comparison panel, scene states and union layout it asserts (`snapshot-comparison` tasks 8, 9, 10). Slip rule: if `analyze` and `cycles` of `analysis-core` are not on `main` by November 8, tasks 4a–8 move to November 12–15 and task 9 to November 16–17; the H9 window (November 22–23) does not move; the slip is logged in the task 4a row. Work happens in the worktree `../HauntMap-kiro-integration` on branch `kiro/kiro-integration`; each task is one commit or a short series with the trailer `Kiro-Task: kiro-integration/<n>` (`<n>` includes the part letter: `1a`, `13b`), merged by the integrator only when `pnpm verify` and, where named, `pnpm verify:e2e -- tests/e2e/live-snapshot.spec.ts` pass on the merge result. Shared files (`package.json`, `pnpm-workspace.yaml`, `.gitignore`, `src/contracts/validate.ts`, `.kiro/steering/ownership.md`, `src/components/App.tsx`, the Vitest and Playwright configuration) change only through the integrator on a one-line request in the task's `docs/kiro-log.md` row. A task is done only when its Verify line holds and its log row is appended the same day, one row per task part in the task-cell format of Requirement 10.4. Two repair passes against the same observed defect, then stop and hand the reproducer to the builder. Credits for this spec total at most 600, assuming about 40 per task; the figure is measured on tasks 1a, 1b, 1c and 3 by November 7 and entered in the ledger; at 540 used, only tasks 12, 14 and 15 may start; if the November 11 ledger review finds the measured figure above 60, the cut order is task 11 first (the unit tests and the recorded session remain the evidence), then task 13b (`docs/crew.md` is then written by the builder from the log). Every *verify* item below is settled by reading the installed version or the landed module and writing the observed value into the file that carries the mark, with a log row.
