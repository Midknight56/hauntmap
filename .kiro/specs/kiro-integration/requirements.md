# Requirements Document

## Introduction

`kiro-integration` is HauntMap's product-level Kiro integration: `packages/hauntmap-mcp`, a stdio MCP server and a `hauntmap` CLI that wrap the same analysis module the app runs in its worker; the `.kiro/settings/mcp.json` registration; the `refactoring.md` steering file; the `verify-on-stop` and `analyze-live` command hooks with `scripts/demo-live.ts` behind the second; the `samples/manor` working copy with `pnpm demo:reset`; the app's **Open live snapshot** control in `src/features/liveSnapshot`; `tests/mcp-agreement.test.ts`; the recorded Kiro CLI session that is the H9 acceptance; and the Crew agent definitions and `docs/kiro-log.md` evidence the Kiro Crew bonus needs. It serves Kiro (as a user of the analysis through MCP), the judge who watches the 1:55–2:30 storyboard segment and then presses **Open live snapshot** in the hosted build, and the builder who records the session. It implements "Kiro integration as a product feature", the `kiro-integration` spec paragraph, work packages H9 and H12, matrix rows 26–29 and the Open live snapshot journey of `plans/hauntmap-implementation-plan.md` (revision 3, 2026-11-03). Owner: kiro, in one worktree (`../HauntMap-kiro-integration`, branch `kiro/kiro-integration`); folders `packages/hauntmap-mcp`, `.kiro/settings`, `.kiro/hooks`, `.kiro/steering/refactoring.md`, `src/features/liveSnapshot`, `samples`, `scripts/demo-reset.ts`, `scripts/demo-live.ts`, `public/demo/live.json`, `tests/kiro`, `tests/mcp-agreement.test.ts`, `tests/e2e/live-snapshot.spec.ts`, `docs/demo`, `docs/acceptance/2026-11-24-h9`, `docs/crew.md`; credit budget 600. Gates: hook observation November 4 and November 10; the pilot's Crew definitions on `main` November 7; H9 (recorded session, `mcp-agreement` green) November 24; H12 (Crew configuration and log) December 2.

Terms. **Workspace root**: the directory that holds `package.json` of the HauntMap repository; the MCP server and the CLI resolve every root against it. **Root**: a directory argument such as `samples/manor`. **Investigation**, **CycleReport**, **TraceResult**, **ComparisonResult**: the `schemaVersion: 1` records of `src/contracts/`. **Relation ID**: `ImportRecord.relationId`, `JSON.stringify([from, targetKey, syntaxKind, dependencyKind])`. **The demo relation**: the relation with `from: "src/notifications/receipt.ts"`, `to: "src/orders/checkout.ts"`, `syntaxKind: "import"`, `dependencyKind: "value"` (*verify* the dependency kind against `public/demo/manor/before/expected.json` when the fixtures agent lands it), whose relation ID is `["src/notifications/receipt.ts",["local","src/orders/checkout.ts"],"import","value"]`. **Live snapshot**: the file `public/demo/live.json`, served at `demo/live.json` relative to the app base, written by `hauntmap analyze`. **Status region**: the one `role="status"` element of the app (`investigation-ui` 10.2); a message segment wrapped in backticks is rendered in `<code>` (`investigation-ui` 10.3). **Compare handoff**: the `compare` function registered through `src/features/investigation/registry.ts` by `snapshot-comparison`, with `CompareArgs = { before: Investigation; after: Investigation | { sample: "manor/after" }; layoutKey: string | null }`. **Observed**: a hook or tool call that was seen firing on the installed Kiro surface and logged in `docs/kiro-log.md` with the date, surface, version and trigger name.

## Requirements

### Requirement 1 — Package, build, launcher and the sample working copy

**User Story:** As Kiro running in the HauntMap repository, I want one buildable package that provides both the MCP server and the CLI from the app's own analysis module, plus a disposable copy of the manor sample I may edit, so that the analysis I call is the analysis the judge sees and the fixtures never change under me.

#### Acceptance Criteria

1. THE SYSTEM SHALL keep the server entry at `packages/hauntmap-mcp/src/index.ts` (built to `packages/hauntmap-mcp/dist/index.js`), the CLI entry at `packages/hauntmap-mcp/src/cli.ts` (built to `dist/cli.js`), the launcher at `packages/hauntmap-mcp/bin/hauntmap.js` (committed, plain JavaScript, no dependencies) and import analysis only from `src/analysis/**` and `src/contracts/**`; `tests/kiro/package-boundary.test.ts` fails if any file under `packages/hauntmap-mcp/src/**` imports from `src/scene`, `src/features`, `src/components` or references `window`, `document` or `fetch`.
2. WHEN `pnpm build:mcp` runs THEN THE SYSTEM SHALL produce `dist/index.js` and `dist/cli.js` as self-contained bundles (bundler pinned at scaffold time; esbuild or tsup, both MIT) such that copying `packages/hauntmap-mcp/dist/` alone to an empty directory and running `node index.js` there answers an MCP `tools/list` request with the four tool names, with no `node_modules` present (`tests/kiro/dist-standalone.test.ts`).
3. THE SYSTEM SHALL expose the root scripts `build:mcp` (`pnpm --filter hauntmap-mcp build`, *verify* the workspace filter syntax on the pinned pnpm), `hauntmap` (`node packages/hauntmap-mcp/bin/hauntmap.js`) and `demo:reset`; WHEN `pnpm hauntmap …` runs while `dist/cli.js` is absent THEN the launcher SHALL print `hauntmap: the CLI is not built. Run pnpm build:mcp first.` to stderr and exit with code 3, writing nothing.
4. THE SYSTEM SHALL keep `samples/manor/` as a committed copy of `public/demo/manor/before/` whose included files are byte-identical to the fixture's (`tests/kiro/sample-copy.test.ts` compares every file with an included extension in both trees and fails on any difference or missing file); `samples/manor` is the only root a Kiro session edits during a live demonstration, and `public/demo/manor/{before,after}` are never edited by this spec or by Kiro sessions it drives.
5. WHEN `pnpm demo:reset` runs THEN THE SYSTEM SHALL delete `samples/manor/`, copy every file of `public/demo/manor/before/` whose extension is one of `.js`, `.jsx`, `.ts`, `.tsx`, `.mjs`, `.mts` to `samples/manor/` at the same relative path (`expected.json` and `sources.json` are not copied), print `demo:reset: samples/manor restored from public/demo/manor/before (<n> files)` and exit 0; running it twice in a row SHALL leave `git status --porcelain samples/` empty.
6. THE SYSTEM SHALL record in `packages/hauntmap-mcp/README.md` the pinned versions and licenses of the MCP TypeScript SDK (package name *verify*), the bundler and the Node version the package targets (*verify*; pin at scaffold time), with the date they were read from the lockfile, and SHALL list them in `docs/third-party-notices.md`.

### Requirement 2 — The Node source loader agrees with the app (matrix row 26)

**User Story:** As a developer comparing what Kiro reported with what the app shows, I want the CLI and the browser to produce identical module IDs, hashes and relation IDs for the same folder, so that an MCP result and an app investigation can be compared relation by relation.

#### Acceptance Criteria

1. THE SYSTEM SHALL load a root with `packages/hauntmap-mcp/src/loader.ts` using exactly the `AnalysisOptions` defaults of `src/contracts/` (`includeExtensions` `.js`, `.jsx`, `.ts`, `.tsx`, `.mjs`, `.mts`; `excludeDirectories` `.git`, `node_modules`, `dist`, `build`, `out`, `.next`, `coverage`; `excludeFilePatterns` `.env`, `.env.*`, `*.pem`, `*.key`, `id_rsa*`; `maxFiles` 1000; `maxFileBytes` 1,048,576; `maxTotalBytes` 26,214,400; `jsToTsFallback: true`), imported from `src/contracts/`, never copied; `tests/kiro/loader.test.ts` asserts `loadSourceSet(root).options` deep-equals the imported defaults with `preset` applied.
2. THE SYSTEM SHALL walk the root depth-first with directory entries sorted by code-point order, SHALL not enter an excluded directory (one `skipped` entry `{ path: "<dir>/", reason: "excluded-dir" }` per excluded directory, matched by segment name at any depth), SHALL skip a file whose basename matches an exclude pattern with reason `secret-pattern`, whose extension is not included with reason `extension`, whose size exceeds 1,048,576 bytes with reason `oversized` (without reading it), and whose first 8,192 bytes contain a NUL byte with reason `binary`; `SourceFile.path` SHALL be relative to the root with forward slashes and no leading `./`.
3. THE SYSTEM SHALL decode each included file as UTF-8 with `new TextDecoder("utf-8")` (a leading byte-order mark is removed, as `Blob.text()` removes it), SHALL not normalize line endings, SHALL set `bytes` to the file size on disk, and SHALL hash with SHA-256 over the UTF-8 encoding of the decoded text through `node:crypto`; for the fixture files `tests/kiro/fixtures/loader-root.json` → `bom.ts` and `crlf.ts`, the hashes SHALL equal those computed in the same test with `new Blob([bytes]).text()` and `crypto.subtle.digest("SHA-256", …)` (the app's path, run on Node's Web APIs).
4. WHEN `pnpm hauntmap analyze samples/manor --out <tmp>` runs and the test analyzes the `SourceSet` produced from the same folder by `scripts/pack-samples.ts` (the app's include rules, `investigation-ui` 1.3) with the same `src/analysis` entry point THEN the two `Investigation`s SHALL have equal sorted module ID lists, equal `sourceHash` per module and equal sorted relation ID lists (`tests/mcp-agreement.test.ts`, case `row 26`); a difference SHALL name the first differing module or relation ID.
5. IF the root has more than 1000 included files THEN THE SYSTEM SHALL stop before parsing and return the error `cap-reached` with the message `Root "<root>" has more than 1000 included files; first excluded: <path>.`; IF included text exceeds 26,214,400 bytes THEN the error `cap-reached` with `Root "<root>" exceeds 25 MiB of included text; first excluded: <path>.`; in both cases no `Investigation` SHALL be produced (`tests/kiro/loader.test.ts` on generated trees of 1,001 files and of 26 files of 1 MiB).
6. THE SYSTEM SHALL resolve a root as `path.resolve(workspaceRoot, root)` followed by `fs.realpath`, and SHALL accept it only when the result equals the workspace root or starts with the workspace root plus the path separator; otherwise it SHALL return `root-outside-workspace` with `Root "<root>" resolves outside the working directory "<workspaceRoot>".` and read nothing; a symbolic link inside the workspace pointing outside it SHALL be rejected the same way (`tests/kiro/loader.test.ts` creates one in a temp workspace).
7. IF the resolved root does not exist or is not a directory THEN THE SYSTEM SHALL return `root-not-found` with `Root "<root>" does not exist or is not a directory.`
8. THE SYSTEM SHALL set `Investigation.sourceLabel` to `live:<root>` where `<root>` is the argument with backslashes replaced by `/`, any leading `./` removed and any trailing `/` removed (`samples/manor` → `live:samples/manor`; `./public/demo/manor/before/` → `live:public/demo/manor/before`).

### Requirement 3 — The MCP server and the tools `analyze`, `cycles`, `who_imports`

**User Story:** As Kiro, I want to ask HauntMap for an investigation, the dependency loops and the importers of a module over stdio with typed arguments and typed errors, so that I can inspect a project's import graph before I change it, without running anything but the parser.

#### Acceptance Criteria

1. WHEN `node packages/hauntmap-mcp/dist/index.js` starts THEN THE SYSTEM SHALL serve the MCP stdio transport of the pinned MCP TypeScript SDK, print nothing to stdout except protocol messages, log to stderr only, and answer `tools/list` with exactly the tools `analyze`, `cycles`, `who_imports` and `compare`, each with a one-sentence description and the JSON Schema input of `design.md` (`tests/kiro/server.test.ts` spawns the built server and lists tools through the SDK client, *verify* the client API names on the pinned version).
2. WHEN `analyze` is called with `{ root, preset? }` THEN THE SYSTEM SHALL return the `Investigation` of that root under `preset` (default `static-value`) with source text omitted, as one text content item containing `JSON.stringify(investigation)` (and as `structuredContent` where the pinned SDK supports it, *verify*); the value SHALL pass `validateInvestigation` of `src/contracts/validate.ts` before it is returned.
3. WHEN `cycles` is called with `{ root, preset? }` THEN THE SYSTEM SHALL return the `CycleReport` computed by `src/analysis/graph` for that preset; for `samples/manor` in its committed state under `static-value` the report SHALL contain exactly one component with members `src/notifications/receipt.ts`, `src/orders/checkout.ts`, `src/payments/charge.ts` and a witness whose `relationIds` include the demo relation ID (matrix row 13 facts, read from `expected.json` by the test).
4. WHEN `who_imports` is called with `{ root, module, preset? }` THEN THE SYSTEM SHALL return the `TraceResult` with `origin: module`, `direction: "imported-by"` and `preset`; for `samples/manor` and `module: "src/orders/checkout.ts"` under `static-value`, `direct` SHALL contain `src/notifications/receipt.ts`.
5. IF `module` is not a module ID of the root's investigation THEN THE SYSTEM SHALL return the error `module-not-found` with `Module "<module>" is not in the analysis of "<root>"; module IDs are paths relative to the root, such as src/orders/checkout.ts.`; IF `preset` is not one of the three presets THEN `invalid-preset` with `Preset "<value>" is not one of static-value, type-inclusive, dynamic-inclusive.`; IF a required argument is missing or not a string THEN `invalid-arguments` with `Argument "<name>" must be a string.`
6. THE SYSTEM SHALL return every error as a tool result flagged as an error (the SDK's error flag, *verify* the field name) whose single text item is `JSON.stringify({ error: { code, message } })` with `code` one of `invalid-arguments`, `invalid-preset`, `root-outside-workspace`, `root-not-found`, `cap-reached`, `module-not-found`, `analysis-failed`; a tool SHALL never throw across the transport, never return a partial result with an error, and never write a file (`tests/kiro/properties.test.ts` P5).
7. THE SYSTEM SHALL execute no file of the analyzed root (no `import()`, `require`, `eval`, child process or `vm` on its content): `tests/kiro/package-boundary.test.ts` fails if `child_process`, `vm`, `eval(` or `new Function(` appears in `packages/hauntmap-mcp/src/**`, and `tests/kiro/no-execution.test.ts` analyzes a root containing `postinstall.js` that writes a marker file and asserts the marker is absent.
8. WHEN `analyze` runs on `samples/manor` on the named laptop THEN THE SYSTEM SHALL answer within 2,000 ms measured from the request to the response inside `tests/kiro/server.test.ts` (a target until recorded in `docs/performance.md` with the device and date).

### Requirement 4 — The `compare` tool and the agreement test (matrix row 27)

**User Story:** As Kiro, I want to compare the untouched manor with my edited copy and get exactly the structural relations I removed and added, so that my final message states what changed in terms the app can confirm.

#### Acceptance Criteria

1. WHEN `compare` is called with `{ rootBefore, rootAfter }` THEN THE SYSTEM SHALL load both roots (Requirement 2), analyze both under `static-value`, call `compare(before, after)` of `src/analysis/graph/compare.ts` and return its `ComparisonResult` with `before.label` and `after.label` equal to the two source labels of 2.8; `compare` takes no preset argument (the plan's open-decisions table, revision 3, records the decision: relation sets are compared over all relations and cycle counts are computed under `static-value`).
2. WHEN `rootBefore` is `public/demo/manor/before` and `rootAfter` is a copy of `samples/manor` in which the demo relation's import declaration has been removed and nothing else changed THEN the result SHALL have `removedRelations` of length 1 with `relationId` equal to the demo relation ID, `addedRelations` of length 0, `removedModules` and `addedModules` empty, `changedModules` equal to `["src/notifications/receipt.ts"]`, `cyclicComponentsBefore` 1 and `cyclicComponentsAfter` 0 (`tests/kiro/compare-tool.test.ts` makes the copy in a temp workspace by deleting the import declaration whose specifier resolves to `src/orders/checkout.ts`).
3. THE SYSTEM SHALL make `tests/mcp-agreement.test.ts` assert, for the pair of 4.2, that `removedRelations` and `addedRelations` returned by the MCP `compare` tool (through the server boundary, parsed from the text item) are deep-equal to those produced by the app's path (`scripts/pack-samples.ts` source sets → `src/analysis` → `src/analysis/graph/compare.ts`), including element order (matrix row 27, programmatic case).
4. WHEN the recorded session of Requirement 9 exists THEN `tests/mcp-agreement.test.ts` SHALL also assert that `removedRelations` and `addedRelations` of `docs/acceptance/2026-11-24-h9/mcp-compare.json` (the `compare` result saved from the session, a top-level `ComparisonResult`) are deep-equal to `comparison.result.removedRelations` and `comparison.result.addedRelations` of `docs/acceptance/2026-11-24-h9/app-comparison-export.json` (the app's Graph JSON export of the same view, whose envelope nests the result at `comparison.result`, `snapshot-comparison` 9.1) (matrix row 27, recorded case; the case is added by task 12 and absent before it).
5. IF either root fails to load THEN THE SYSTEM SHALL return that root's error (Requirement 2) with the message prefixed by `rootBefore: ` or `rootAfter: `, and no comparison.
6. THE SYSTEM SHALL return a `ComparisonResult` that passes `validateComparison` of `src/contracts/validate.ts`; `addedRelations` and `removedRelations` SHALL be sorted by `relationId` and the three module lists SHALL be sorted, as `compare.ts` guarantees; the tool SHALL not re-sort or alter them (`tests/kiro/compare-tool.test.ts` compares against a direct `compare.ts` call).

### Requirement 5 — The `hauntmap` CLI

**User Story:** As the hook and the builder, I want `hauntmap analyze` and `hauntmap compare` to write schema-valid JSON files with clear exit codes, so that `public/demo/live.json` is always either absent or valid and a failed run is visible in the hook output.

#### Acceptance Criteria

1. THE SYSTEM SHALL accept `hauntmap analyze <root> --out <file> [--preset static-value|type-inclusive|dynamic-inclusive]` and `hauntmap compare <before> <after> --out <file>`; any other invocation SHALL print the two usage lines of `design.md` to stderr and exit with code 2.
2. WHEN `analyze` succeeds THEN THE SYSTEM SHALL write the `Investigation` (source omitted) as JSON with two-space indentation and a trailing newline to `<file>`, writing first to `<file>.tmp` in the same directory and renaming it over `<file>`, print `analyze: <modules> modules, <relations> relations, <diagnostics> diagnostics → <file>` to stdout and exit 0; `<relations>` counts distinct relation IDs.
3. WHEN `compare` succeeds THEN THE SYSTEM SHALL write the `ComparisonResult` the same way and print `compare: <removed> removed, <added> added, <changed> changed modules → <file>`.
4. THE SYSTEM SHALL exit with code 4 and print `hauntmap: <message>` to stderr for `root-outside-workspace`, `root-not-found` and `cap-reached` (messages of Requirement 2), with code 2 for `invalid-preset`, with code 6 and `hauntmap: cannot write <file> (<error code>).` when the output cannot be written (missing parent directory, permission), and with code 5 and `hauntmap: internal error, output failed validation: <first error>` when the produced value fails the validator; in every non-zero case `<file>` SHALL be left as it was and no `<file>.tmp` SHALL remain (`tests/kiro/cli.test.ts` runs the built CLI in a temp workspace for each case).
5. THE SYSTEM SHALL resolve `<root>` and `<file>` against the current working directory, which must be the workspace root: IF the current directory holds no `package.json` with `"name": "hauntmap"` (*verify* the root package name at scaffold time) THEN the CLI SHALL print `hauntmap: run from the HauntMap repository root (no package.json named hauntmap in <cwd>).` and exit 4.
6. WHEN `pnpm hauntmap analyze samples/manor --out public/demo/live.json` runs on a committed, unedited `samples/manor` THEN the resulting file SHALL validate, have 40 modules, `sourceLabel` `live:samples/manor`, no `text` property on any element and no property anywhere whose value contains a newline followed by `import ` (a guard against source text leaking into the file), and running the command twice on an unchanged `samples/manor` SHALL produce byte-identical files (`cmp` prints nothing).

### Requirement 7 — The `refactoring.md` steering file

**User Story:** As Kiro changing imports in this repository, I want a short standing instruction to check loops before an import change and to compare after it, so that my final message reports exactly which relations I removed and added and never relabels a graph change as a runtime guarantee.

#### Acceptance Criteria

1. THE SYSTEM SHALL keep `.kiro/steering/refactoring.md` with front matter `inclusion: always` (*verify* the front-matter keys on the installed version), under 60 lines, in imperative sentences, naming the server `hauntmap` and the tools `cycles`, `compare`, `who_imports` and `analyze`, the roots `samples/manor` and `public/demo/manor/before`, the command `pnpm demo:reset` and the `.hauntmap/before/` copy rule of `design.md`; `tests/kiro/steering.test.ts` asserts the front matter, the line count and the presence of each name.
2. THE SYSTEM SHALL instruct: before changing, adding, removing or moving any import, re-export or module file in an analyzed root, call `cycles(root, "static-value")` and keep its component list; after the change, call `compare(rootBefore, rootAfter)` with the untouched copy as `rootBefore`; end the final message with the `relationId` of every element of `removedRelations` and `addedRelations`, the two labels and the two cycle counts, copied from the tool result; and state `compare was not run` when it was not.
3. THE SYSTEM SHALL instruct that `public/demo/manor/before`, `public/demo/manor/after` and `public/demo/annex` are fixtures owned by `analysis-core` and are never edited; that live edits go to `samples/manor`; that `pnpm demo:reset` restores it; and that a graph change is a structural fact, not a correctness, safety or performance claim (the claims policy restated in one line, not repeated).
4. WHEN a Kiro CLI session with the steering file active is asked to remove one import in `samples/manor` THEN Kiro SHALL call `cycles` before editing and `compare` after editing without being told to in the prompt, and its final message SHALL contain the demo relation ID under a removed heading; the session is the one recorded in Requirement 9 and its transcript is the evidence (`docs/acceptance/2026-11-24-h9/transcript.md`). THE SYSTEM SHALL keep every expected result of that session (the component members, the demo relation, the counts `1 → 0`, the order of calls) out of the steering file, so that the transcript shows tool results rather than a restatement of what the file told Kiro to expect: `tests/kiro/steering.test.ts` fails if `refactoring.md` contains `receipt.ts`, `checkout.ts`, `charge.ts`, `exactly one removed` or `1 → 0`; the expected sequence lives only in `docs/demo/h9-session-script.md`, which the builder reads and Kiro does not.
5. IF the steering file is not loaded by the installed version (front-matter keys differ) THEN the keys SHALL be corrected to the observed ones and the observation logged; the content rules of 7.2 and 7.3 SHALL not change.

### Requirement 8 — Open live snapshot (matrix row 28)

**User Story:** As a judge who just watched Kiro remove an import, I want one control in the app that loads the snapshot Kiro's hook wrote and shows it as the newer revision against the manor I am looking at, with every unchanged room exactly where it was, so that I can confirm the change myself.

#### Acceptance Criteria
