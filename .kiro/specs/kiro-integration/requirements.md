# Requirements Document

## Introduction

`kiro-integration` is HauntMap's product-level Kiro integration: `packages/hauntmap-mcp`, a stdio MCP server and a `hauntmap` CLI that wrap the same analysis module the app runs in its worker; the `.kiro/settings/mcp.json` registration; the `refactoring.md` steering file; the `verify-on-stop` and `analyze-live` command hooks with `scripts/demo-live.ts` behind the second; the `samples/manor` working copy with `pnpm demo:reset`; the app's **Open live snapshot** control in `src/features/liveSnapshot`; `tests/mcp-agreement.test.ts`; the recorded Kiro CLI session that is the H9 acceptance; and the `docs/kiro-log.md` evidence. It serves Kiro (as a user of the analysis through MCP), the judge who watches the 1:55–2:30 storyboard segment and then presses **Open live snapshot** in the hosted build, and the owner of the repository. It implements "Kiro integration as a product feature", the `kiro-integration` spec paragraph, work packages H9 and H12, matrix rows 26–29 and the Open live snapshot journey of `plans/hauntmap-implementation-plan.md` (revision 3, 2026-11-03), as changed by `.kiro/steering/revision-2026-11-16.md`, which wins where the two differ. Owner: Kiro, in the main checkout, on its own branch; folders `packages/hauntmap-mcp`, `.kiro/settings`, `.kiro/hooks`, `.kiro/steering/refactoring.md`, `src/features/liveSnapshot`, `samples`, `scripts/sampleTree.ts`, `scripts/demo-reset.ts`, `scripts/demo-live.ts`, `public/demo/live.json`, `tests/kiro` (including `tests/kiro/e2e/live-snapshot.spec.ts`), `tests/mcp-agreement.test.ts`, `docs/demo`, `docs/acceptance/h9-session`. Work order and gates: `.kiro/steering/revision-2026-11-16.md` (tasks 1a–8 after `analysis-core`; tasks 9–12, 14 and 15 after `investigation-ui` and `snapshot-comparison`); dates in this document are history, not deadlines. The Crew is not used: Requirement 10.1–10.3 are withdrawn.

Environment. Every task runs on Windows in PowerShell, driven by the Kiro CLI with no person at the keyboard. Commands in acceptance criteria are written so they run there: paths under `.hauntmap/` instead of `/tmp`, `git diff --no-index --exit-code <a> <b>` (or comparing `Get-FileHash` values) instead of `cmp`, `Select-String` instead of `grep`, `(Get-Content <f>).Count` instead of `wc -l`. Where a criterion asks for a screenshot, a transcript excerpt file (Markdown, the raw output pasted between fences, with the command that produced it) is accepted instead. Where a criterion needs a person, it says **Needs a person**; until a person does it, the item is recorded as not done, never as done.

Files of other owners. `.kiro/steering/ownership.md` gives this spec only part of the folders above (`packages/hauntmap-mcp/**`, `samples/**`, `scripts/demo-reset.ts`, `scripts/demo-live.ts`, `public/demo/live.json`, `src/features/liveSnapshot/**`, `tests/kiro/**`) and the one file `src/contracts/validate.ts`. The other paths above are listed in no row. This spec also needs one-line changes in files that belong to other specs: the root configuration files of `analysis-core` (`package.json` scripts, `pnpm-workspace.yaml` `packages`, `vitest.config.ts` for `.tsx` tests and the global build setup, `eslint.config.js` ignores for `packages/*/dist/**` and `samples/**`, the Playwright configuration once it exists), and `src/components/App.tsx` of `investigation-ui` (one `registerLiveSnapshot(...)` call). Under the ownership rule a task that needs one of these stops and says so. Each task that needs such a change names it; it goes ahead only after `.kiro/steering/ownership.md` lists the change as an exception for `kiro-integration` (as it already does for `src/contracts/validate.ts`).

Terms. **Workspace root**: the directory that holds `package.json` of the HauntMap repository; the MCP server and the CLI resolve every root against it. **Root**: a directory argument such as `samples/manor`. **Investigation**, **CycleReport**, **TraceResult**, **ComparisonResult**: the `schemaVersion: 1` records of `src/contracts/`. **Relation ID**: `ImportRecord.relationId`, `JSON.stringify([from, targetKey, syntaxKind, dependencyKind])`. **The demo relation**: the relation with `from: "src/notifications/receipt.ts"`, `to: "src/orders/checkout.ts"`, `syntaxKind: "import"`, `dependencyKind: "value"` (read on 2026-11-16 from `public/demo/manor/before/expected.json`, the import of `src/notifications/receipt.ts` at line 3, column 1, specifier `../orders/checkout`; its use is line 13; the field `receiptToCheckout` holds `{ "specifier": "../orders/checkout", "importLine": 3, "useLine": 13 }`), whose relation ID is `["src/notifications/receipt.ts",["local","src/orders/checkout.ts"],"import","value"]`. **Live snapshot**: the file `public/demo/live.json`, served at `demo/live.json` relative to the app base, written by `hauntmap analyze`. **Status region**: the one `role="status"` element of the app (`investigation-ui` 10.2); a message segment wrapped in backticks is rendered in `<code>` (`investigation-ui` 10.3). **Compare handoff**: the `compare` function registered through `src/features/investigation/registry.ts` by `snapshot-comparison`, with `CompareArgs = { before: Investigation; after: Investigation | { sample: "manor/after" }; layoutKey: string | null }`. **Observed**: a hook or tool call that was seen firing on the installed Kiro surface and logged in `docs/kiro-log.md` with the date, surface, version and trigger name. A hook counts as seen firing only when its own output, or a side effect only it produces, appears in a saved transcript or file; a session in which no hook output reached the transcript records "not observed". **Headless session**: a Kiro CLI 3.3.0 session started from PowerShell with a prompt as argument and its output saved to a file (the flags are read from `kiro-cli chat --help` of the installed version, *verify*); it is how Kiro observes hooks and tool calls without a person. **Analysis entry points**: `analyze`, `selectSources`, `findCycles`, `trace` and `DEFAULT_ANALYSIS_OPTIONS`, all imported from `src/analysis/index.ts` (the only export file of `analysis-core`), and `compareInvestigations` from `src/analysis/graph/compare.ts` (`snapshot-comparison`).

## Requirements

### Requirement 1 — Package, build, launcher and the sample working copy

**User Story:** As Kiro running in the HauntMap repository, I want one buildable package that provides both the MCP server and the CLI from the app's own analysis module, plus a disposable copy of the manor sample I may edit, so that the analysis I call is the analysis the judge sees and the fixtures never change under me.

#### Acceptance Criteria

1. THE SYSTEM SHALL keep the server entry at `packages/hauntmap-mcp/src/index.ts` (built to `packages/hauntmap-mcp/dist/index.js`), the CLI entry at `packages/hauntmap-mcp/src/cli.ts` (built to `dist/cli.js`), the launcher at `packages/hauntmap-mcp/bin/hauntmap.js` (committed, plain JavaScript, no dependencies) and import analysis only from `src/analysis/index.ts`, `src/analysis/graph/compare.ts`, `src/contracts/types.ts` and `src/contracts/validate.ts`; `tests/kiro/package-boundary.test.ts` fails if any file under `packages/hauntmap-mcp/src/**` imports from `src/scene`, `src/features`, `src/components`, from any other file under `src/analysis/**` (deep paths such as `src/analysis/parser/analyze`), or references `window`, `document` or `fetch`; no file under `packages/hauntmap-mcp/src/**` declares a function named `extractImports`, `resolveSpecifier`, `findCycles`, `trace` or `tarjan`, or imports a parser package (`tests/analysis-boundary.test.ts` check 2 of `analysis-core` already scans `packages/` and skips `dist/`).
2. WHEN `pnpm build:mcp` runs THEN THE SYSTEM SHALL produce `dist/index.js` and `dist/cli.js` as self-contained bundles (bundler pinned at scaffold time; esbuild or tsup, both MIT) such that copying `packages/hauntmap-mcp/dist/` alone to an empty directory under the system temp directory (outside the repository, so that no parent `package.json` or `node_modules` is found) and running `node index.js` there answers an MCP `tools/list` request with the four tool names (`tests/kiro/dist-standalone.test.ts`); the bundle format (ESM or CommonJS) is chosen so that Node 24 runs it without a `package.json` beside it, and recorded in `README.md`.
3. THE SYSTEM SHALL expose the root scripts `build:mcp` (`pnpm --filter hauntmap-mcp build`, *verify* the filter syntax on the pinned pnpm 12.3.4), `hauntmap` (`node packages/hauntmap-mcp/bin/hauntmap.js`), `demo:reset` (`tsx scripts/demo-reset.ts`) and `demo:live` (`tsx scripts/demo-live.ts`), the runner being `tsx`, as `pack:samples` uses it; WHEN `pnpm hauntmap …` runs while `dist/cli.js` is absent THEN the launcher SHALL print `hauntmap: the CLI is not built. Run pnpm build:mcp first.` to stderr and exit with code 3, writing nothing. The launcher SHALL load `dist/cli.js` through `import(pathToFileURL(path).href)`, because `import()` of a Windows path such as `D:\…` fails.
4. THE SYSTEM SHALL keep `samples/manor/` as a committed copy of `public/demo/manor/before/` whose included files are byte-identical to the fixture's (`tests/kiro/sample-copy.test.ts` compares every file with an included extension in both trees and fails on any difference or missing file); `samples/manor` is the only root a Kiro session edits during a live demonstration, and `public/demo/manor/{before,after}` are never edited by this spec or by Kiro sessions it drives.
5. WHEN `pnpm demo:reset` runs THEN THE SYSTEM SHALL delete `samples/manor/`, copy every file of `public/demo/manor/before/` whose extension is one of `.js`, `.jsx`, `.ts`, `.tsx`, `.mjs`, `.mts` to `samples/manor/` at the same relative path (`expected.json` and `sources.json` are not copied), print `demo:reset: samples/manor restored from public/demo/manor/before (<n> files)` (`<n>` is 40 for the committed fixture) and exit 0; running it twice in a row SHALL leave `git status --porcelain samples/` empty.
6. THE SYSTEM SHALL record in `packages/hauntmap-mcp/README.md` the pinned versions and licenses of the MCP TypeScript SDK (package name *verify*), the bundler and the Node version the package targets (24, from `engines` of the root `package.json`; the installed `node --version` is recorded too), with the date they were read from the lockfile, and SHALL list them in `docs/third-party-notices.md`. Because `pnpm-workspace.yaml` sets `allowBuilds: esbuild: false`, the README SHALL also record whether the chosen bundler runs with esbuild's install script denied (`pnpm exec esbuild --version` succeeds) or which change to `allowBuilds` was made.

### Requirement 2 — The Node source loader agrees with the app (matrix row 26)

**User Story:** As a developer comparing what Kiro reported with what the app shows, I want the CLI and the browser to produce identical module IDs, hashes and relation IDs for the same folder, so that an MCP result and an app investigation can be compared relation by relation.

#### Acceptance Criteria

1. THE SYSTEM SHALL load a root with `packages/hauntmap-mcp/src/loader.ts` using exactly the `AnalysisOptions` defaults of `src/contracts/` (`includeExtensions` `.js`, `.jsx`, `.ts`, `.tsx`, `.mjs`, `.mts`; `excludeDirectories` `.git`, `node_modules`, `dist`, `build`, `out`, `.next`, `coverage`; `excludeFilePatterns` `.env`, `.env.*`, `*.pem`, `*.key`, `id_rsa*`; `maxFiles` 1000; `maxFileBytes` 1,048,576; `maxTotalBytes` 26,214,400; `jsToTsFallback: true`), imported from `src/analysis/index.ts` (which re-exports it from `src/contracts/options.ts`; it includes `preset: "static-value"`), never copied; `tests/kiro/loader.test.ts` asserts that the `options` of the `Investigation` produced for a root deep-equal `{ ...DEFAULT_ANALYSIS_OPTIONS, preset }` (a `SourceSet` has no `options` field).
2. THE SYSTEM SHALL walk the root depth-first with directory entries sorted by code-point order and SHALL not enter an excluded directory (one `skipped` entry `{ path: "<dir>/", reason: "excluded-dir" }` per excluded directory, matched by segment name at any depth); every other file SHALL be passed, as a `SourceFile`, to `selectSources` of `src/analysis` with `rootLabel` and the options, so that the classification and its order are the app's: `secret-pattern` (basename matches an exclude pattern), `extension`, `oversized` (size over 1,048,576 bytes, with the `oversized` diagnostic) and `binary` (U+0000 within the first 8,192 UTF-16 code units of the decoded text, the rule of `selectSources`); the loader SHALL read the bytes of a file only when its basename matches no exclude pattern, its extension is included and its size is at most `maxFileBytes`, and SHALL pass `text: ""` with `bytes` set to the size on disk otherwise; `SourceFile.path` SHALL be relative to the root with forward slashes and no leading `./`; the diagnostics `selectSources` returns SHALL be passed to `analyze` as `selectionDiagnostics`.
3. THE SYSTEM SHALL decode each included file as UTF-8 with `new TextDecoder("utf-8")` (a leading byte-order mark is removed, as `Blob.text()` removes it), SHALL not normalize line endings, SHALL set `bytes` to the file size on disk, and SHALL pass `analyze` a `HashFn` that returns the SHA-256 hex of the UTF-8 encoding of the text through `node:crypto` (`analyze` calls the passed hash function for every module; read from `src/analysis/parser/analyze.ts` on 2026-11-16); for the fixture files `tests/kiro/fixtures/loader-root.json` → `bom.ts` and `crlf.ts`, the hashes SHALL equal those computed in the same test with `new Blob([bytes]).text()` and `crypto.subtle.digest("SHA-256", …)` (the app's path, run on Node's Web APIs).
4. WHEN `pnpm hauntmap analyze samples/manor --out <tmp>` runs and the test analyzes `public/demo/manor/before/sources.json` (the file the app's `loadSample("manor/before")` fetches, written by `scripts/pack-samples.ts` of `analysis-core`; each entry becomes a `SourceFile` with `bytes` equal to the UTF-8 length of its text) through `selectSources` and `analyze` with a Web Crypto hash, as the analysis worker does, THEN the two `Investigation`s SHALL have equal sorted module ID lists, equal `sourceHash` per module and equal sorted relation ID lists (`tests/mcp-agreement.test.ts`, case `row 26`); a difference SHALL name the first differing module or relation ID. `samples/manor` is byte-identical to `public/demo/manor/before` (1.4), so this compares the Node route and the app route on the same files.
5. IF the root has more than 1000 included files THEN THE SYSTEM SHALL stop before parsing and return the error `cap-reached` with the message `Root "<root>" has more than 1000 included files; first excluded: <path>.`; IF included text exceeds 26,214,400 bytes THEN the error `cap-reached` with `Root "<root>" exceeds 25 MiB of included text; first excluded: <path>.`; `<path>` is the `module` of the `cap-reached` diagnostic that `selectSources` returns (the 1,001st included path in code-unit order, or the file whose running total first exceeds the limit); in both cases no `Investigation` SHALL be produced (`tests/kiro/loader.test.ts` on generated trees of 1,001 files and of 26 files of 1,048,576 bytes each: 25 such files total exactly 26,214,400 bytes, which is not over the limit, so the 26th sorted name is the first excluded).
6. THE SYSTEM SHALL resolve a root as `path.resolve(workspaceRoot, root)` followed by `fs.realpath`, and SHALL accept it only when the result equals the workspace root or starts with the workspace root plus the path separator; otherwise it SHALL return `root-outside-workspace` with `Root "<root>" resolves outside the working directory "<workspaceRoot>".` and read nothing; a symbolic link or directory junction inside the workspace pointing outside it SHALL be rejected the same way (`tests/kiro/loader.test.ts` creates one in a temp workspace; on Windows it creates a directory junction, `fs.symlink(target, path, "junction")`, which needs no administrator right; the workspace root itself is passed through `fs.realpath` so that drive-letter case and short names compare equal).
7. IF the resolved root does not exist or is not a directory THEN THE SYSTEM SHALL return `root-not-found` with `Root "<root>" does not exist or is not a directory.`
8. THE SYSTEM SHALL set `Investigation.sourceLabel` to `live:<root>` where `<root>` is the argument with backslashes replaced by `/`, any leading `./` removed and any trailing `/` removed (`samples/manor` → `live:samples/manor`; `./public/demo/manor/before/` → `live:public/demo/manor/before`).

### Requirement 3 — The MCP server and the tools `analyze`, `cycles`, `who_imports`

**User Story:** As Kiro, I want to ask HauntMap for an investigation, the dependency loops and the importers of a module over stdio with typed arguments and typed errors, so that I can inspect a project's import graph before I change it, without running anything but the parser.

#### Acceptance Criteria

1. WHEN `node packages/hauntmap-mcp/dist/index.js` starts THEN THE SYSTEM SHALL serve the MCP stdio transport of the pinned MCP TypeScript SDK, print nothing to stdout except protocol messages, log to stderr only, and answer `tools/list` with exactly the tools `analyze`, `cycles`, `who_imports` and `compare`, each with a one-sentence description and the JSON Schema input of `design.md`, returned verbatim (the SDK's high-level registration converts schema objects of its own schema library; the server therefore answers `tools/list` with the JSON Schemas of `design.md` unchanged, through whichever SDK interface allows it, *verify* on the pinned version) (`tests/kiro/server.test.ts` spawns the built server and lists tools through the SDK client, *verify* the client API names on the pinned version).
2. WHEN `analyze` is called with `{ root, preset? }` THEN THE SYSTEM SHALL return the `Investigation` of that root under `preset` (default `static-value`) with source text omitted, as one text content item containing `JSON.stringify(investigation)` (and as `structuredContent` where the pinned SDK supports it, *verify*); the value SHALL pass `validateInvestigation` of `src/contracts/validate.ts` before it is returned.
3. WHEN `cycles` is called with `{ root, preset? }` THEN THE SYSTEM SHALL return the `CycleReport` that `findCycles(investigation, preset)` of `src/analysis` computes; for `samples/manor` in its committed state under `static-value` the report SHALL contain exactly one component with members `src/notifications/receipt.ts`, `src/orders/checkout.ts`, `src/payments/charge.ts` and a witness whose `relationIds` include the demo relation ID (in `expected.json` it is the first of the three; matrix row 13 facts, read from `expected.json` by the test).
4. WHEN `who_imports` is called with `{ root, module, preset? }` THEN THE SYSTEM SHALL return the `TraceResult` of `trace(investigation, module, "imported-by", preset)` of `src/analysis`, with `origin: module`, `direction: "imported-by"` and `preset`; for `samples/manor` and `module: "src/orders/checkout.ts"` under `static-value`, `direct` SHALL equal `["src/notifications/receipt.ts"]` (the only import of `../orders/checkout` in `expected.json`).
5. IF `module` is not a module ID of the root's investigation THEN THE SYSTEM SHALL return the error `module-not-found` with `Module "<module>" is not in the analysis of "<root>"; module IDs are paths relative to the root, such as src/orders/checkout.ts.`; IF `preset` is not one of the three presets THEN `invalid-preset` with `Preset "<value>" is not one of static-value, type-inclusive, dynamic-inclusive.`; IF a required argument is missing or not a string THEN `invalid-arguments` with `Argument "<name>" must be a string.`
6. THE SYSTEM SHALL return every error as a tool result flagged as an error (the SDK's error flag, *verify* the field name) whose single text item is `JSON.stringify({ error: { code, message } })` with `code` one of `invalid-arguments`, `invalid-preset`, `root-outside-workspace`, `root-not-found`, `cap-reached`, `module-not-found`, `analysis-failed`; a tool SHALL never throw across the transport, never return a partial result with an error, and never write a file (`tests/kiro/properties.test.ts` P5).
7. THE SYSTEM SHALL execute no file of the analyzed root (no `import()`, `require`, `eval`, child process or `vm` on its content): `tests/kiro/package-boundary.test.ts` fails if `child_process`, `vm`, `eval(` or `new Function(` appears in `packages/hauntmap-mcp/src/**`, and `tests/kiro/no-execution.test.ts` analyzes a root containing `postinstall.js` that writes a marker file and asserts the marker is absent.
8. WHEN `analyze` runs on `samples/manor` THEN THE SYSTEM SHALL answer within 2,000 ms measured from the request to the response inside `tests/kiro/server.test.ts` (a target until recorded in `docs/performance.md` with the machine Kiro ran on, named by the CPU model and memory read from `Get-CimInstance Win32_Processor` and `Win32_ComputerSystem`, and the date).

### Requirement 4 — The `compare` tool and the agreement test (matrix row 27)

**User Story:** As Kiro, I want to compare the untouched manor with my edited copy and get exactly the structural relations I removed and added, so that my final message states what changed in terms the app can confirm.

#### Acceptance Criteria

1. WHEN `compare` is called with `{ rootBefore, rootAfter }` THEN THE SYSTEM SHALL load both roots (Requirement 2), analyze both under `static-value`, call `compareInvestigations(before, after)` of `src/analysis/graph/compare.ts` and return the `result` of its `{ ok: true, result, detail }` outcome (the `detail` is not returned), with `before.label` and `after.label` equal to the two source labels of 2.8; an `{ ok: false, error }` outcome SHALL become the error `analysis-failed` with the message `The snapshots cannot be compared: <error.message>.`; `compare` takes no preset argument (the plan's open-decisions table, revision 3, records the decision: relation sets are compared over all relations and cycle counts are computed under `static-value`).
2. WHEN `rootBefore` is `public/demo/manor/before` and `rootAfter` is a copy of `samples/manor` in which the demo relation's import declaration has been removed and nothing else changed THEN the result SHALL have `removedRelations` of length 1 with `relationId` equal to the demo relation ID, `addedRelations` of length 0, `removedModules` and `addedModules` empty, `changedModules` equal to `["src/notifications/receipt.ts"]`, `before.moduleCount` and `after.moduleCount` 40, `before.relationCount` 72 and `after.relationCount` 71 (the 72 imports of `expected.json` have 72 distinct relation IDs, and the copy loses one), `cyclicComponentsBefore` 1 and `cyclicComponentsAfter` 0 (`tests/kiro/compare-tool.test.ts` makes the copy in a temp workspace by deleting the two lines of `src/notifications/receipt.ts` whose numbers are `receiptToCheckout.importLine` and `receiptToCheckout.useLine` of `expected.json` (lines 3 and 13); the test reads the counts from `expected.json` rather than hardcoding them).
3. THE SYSTEM SHALL make `tests/mcp-agreement.test.ts` assert, for the pair of 4.2, that `removedRelations` and `addedRelations` returned by the MCP `compare` tool (through the server boundary, parsed from the text item) are deep-equal to those produced by the app's path (`public/demo/manor/before/sources.json` for the earlier side and the copy's files for the newer side, each through `selectSources` → `analyze` with a Web Crypto hash → `compareInvestigations`), including element order (matrix row 27, programmatic case).
4. WHEN the recorded session of Requirement 9 exists THEN `tests/mcp-agreement.test.ts` SHALL also assert that `removedRelations` and `addedRelations` of `docs/acceptance/h9-session/mcp-compare.json` (the `compare` result saved from the session, a top-level `ComparisonResult`) are deep-equal to `comparison.result.removedRelations` and `comparison.result.addedRelations` of `docs/acceptance/h9-session/app-comparison.json` (the app's comparison of the same view, read through the development hook as `compareStore.getState().result` and saved as `{ comparison: { result } }`; the export feature of `snapshot-comparison` is not built, revision of 2026-11-16) (matrix row 27, recorded case; the case is added by task 12 and absent before it).
5. IF either root fails to load THEN THE SYSTEM SHALL return that root's error (Requirement 2) with the message prefixed by `rootBefore: ` or `rootAfter: `, and no comparison.
6. THE SYSTEM SHALL return a `ComparisonResult` that passes `validateComparison` of `src/contracts/validate.ts`; `addedRelations` and `removedRelations` SHALL be sorted by `relationId` and the three module lists SHALL be sorted, as `compare.ts` guarantees; the tool SHALL not re-sort or alter them (`tests/kiro/compare-tool.test.ts` compares against a direct `compareInvestigations` call).

### Requirement 5 — The `hauntmap` CLI

**User Story:** As the hook and the owner of the repository, I want `hauntmap analyze` and `hauntmap compare` to write schema-valid JSON files with clear exit codes, so that `public/demo/live.json` is always either absent or valid and a failed run is visible in the hook output.

#### Acceptance Criteria

1. THE SYSTEM SHALL accept `hauntmap analyze <root> --out <file> [--preset static-value|type-inclusive|dynamic-inclusive]` and `hauntmap compare <before> <after> --out <file>`; any other invocation SHALL print the two usage lines of `design.md` to stderr and exit with code 2.
2. WHEN `analyze` succeeds THEN THE SYSTEM SHALL write the `Investigation` (source omitted) as JSON with two-space indentation and a trailing newline to `<file>`, writing first to `<file>.tmp` in the same directory and renaming it over `<file>`, print `analyze: <modules> modules, <relations> relations, <diagnostics> diagnostics → <file>` to stdout and exit 0; `<relations>` counts distinct relation IDs.
3. WHEN `compare` succeeds THEN THE SYSTEM SHALL write the `ComparisonResult` the same way and print `compare: <removed> removed, <added> added, <changed> changed modules → <file>`.
4. THE SYSTEM SHALL exit with code 4 and print `hauntmap: <message>` to stderr for `root-outside-workspace`, `root-not-found` and `cap-reached` (messages of Requirement 2), with code 2 for `invalid-preset`, with code 6 and `hauntmap: cannot write <file> (<error code>).` when the output cannot be written (missing parent directory, permission), and with code 5 and `hauntmap: internal error, output failed validation: <first error>` when the produced value fails the validator; in every non-zero case `<file>` SHALL be left as it was and no `<file>.tmp` SHALL remain (`tests/kiro/cli.test.ts` runs the built CLI in a temp workspace for each case).
5. THE SYSTEM SHALL resolve `<root>` and `<file>` against the current working directory, which must be the workspace root: IF the current directory holds no `package.json` with `"name": "hauntmap"` (the name of the root `package.json`, read on 2026-11-16) THEN the CLI SHALL print `hauntmap: run from the HauntMap repository root (no package.json named hauntmap in <cwd>).` and exit 4.
6. WHEN `pnpm hauntmap analyze samples/manor --out public/demo/live.json` runs on a committed, unedited `samples/manor` THEN the resulting file SHALL validate, have 40 modules, `sourceLabel` `live:samples/manor`, no `text` property on any element and no property anywhere whose value contains a newline followed by `import ` (a guard against source text leaking into the file), the CLI SHALL print `analyze: 40 modules, 72 relations, 1 diagnostics → public/demo/live.json` (40 modules, 72 distinct relation IDs and the one `unresolved` diagnostic of `expected.json`), and running the command twice on an unchanged `samples/manor` SHALL produce byte-identical files (`git diff --no-index --exit-code` exits 0). On Windows the rename over an existing `<file>` can fail with `EPERM` or `EBUSY` while another process holds the file open; the CLI SHALL retry the rename up to 5 times 100 ms apart before reporting exit 6.

### Requirement 6 — Hooks: `verify-on-stop` and `analyze-live` (matrix row 29)

**User Story:** As the owner of the repository, I want two command hooks whose trigger names were observed on the installed Kiro surface before anyone cites them, so that every Kiro session re-verifies the repository and refreshes the live snapshot without a human remembering to.
