# Requirements Document

## Introduction

`investigation-ui` is the visible product of HauntMap: the landing screen with its sample gallery, the illustrated 2.5D cutaway map (PixiJS behind an imperative adapter), the dagre layout adapter that runs inside the layout worker, and the semantic React interface (search, legend, tooltips, inspector, evidence list, the loop and who-imports panels, the three optional investigation steps) that shares one selection with the scene. It serves the judge who opens the hosted demo and the developer who investigates a dependency or reviews a small refactor. It implements "Main user journeys" (first visit, investigate a cycle, inspect a proposed change), "Visual language tied to function", "Layout and rendering", work packages H4 and H7, matrix rows 11, 15, 17, 18 and 19 (sample portion), and the performance targets (not measured under the revision) of `plans/hauntmap-implementation-plan.md` (revision 3, 2026-11-03), on top of the `Investigation`, `CycleReport` and `TraceResult` contracts of `analysis-core`. Owner: Kiro, the one writer in the main checkout, under the revision of 16 November 2026 (`.kiro/steering/revision-2026-11-16.md`): tasks 1a to 13 and 15 are done; task 14 is reduced to the renderer fallback test; task 0 (the spike) is not done and the layout engine is dagre. The `intake` spec (local folder and GitHub by URL, matrix rows 21, 22 and 30) is not built, so nothing in this spec depends on it and the landing screen has only `Explore the manor` and `Explore the annex`. Export is not built by any spec under the revision, so the `export` slot stays empty unless a stub fills it in a test. Art-kit integration (H6) and the capture script (H8) are outside this spec. Every statement that needs a named laptop, a person or a second browser (1.8, 1.9, 3.8, 4.8, 9.6, 12.5, 12.6) is left for the owner and stays a target. Browser tests run headless only.

Terms used below. **Investigation**: the `Investigation` record (`schemaVersion: 1`) of `src/contracts/`. **Module ID**: `ModuleRecord.id`, a normalized relative path. **Relation ID** and **occurrence ID**: `ImportRecord.relationId` and `ImportRecord.occurrenceId`. **Preset**: `static-value` (default), `type-inclusive` or `dynamic-inclusive`; the preset rule lives in `src/analysis/graph` and is never reimplemented here. **Wing**: the directory part of a module ID (`src/orders` for `src/orders/checkout.ts`); modules at the root form the wing `(root)`. **Room**: one module. **Door**: one relation with `resolution: "local"`, deduplicated by relation ID, drawn on the importer's room with an arrow to the target room. **Sealed doorway**: one relation with resolution `external`, `unresolved` or `unsupported`, drawn on the importer's room. **Corridor**: the drawn route of a cycle witness or of a trace path. **Selection**: the single `Selection` value of `src/features/investigation/store.ts`. **Route filter**: the module and relation IDs of the current witness, trace path or focus; a room outside it is **subdued**. **Map view** and **Evidence view**: the two tabs of the investigation screen; the Evidence view is the complete semantic alternative to the canvas. **Status region**: the one `role="status"` element of the app. **Named laptop**: a machine the owner names in `docs/performance.md`; no row exists until the owner records one. **Development build**: a build in which the hook `window.__hauntmap` exists: `pnpm dev`, or the production build `pnpm build:devhook` (Vite mode `devhook`, whose `.env.devhook` sets `VITE_HAUNTMAP_DEVHOOK=1`; the `dev` Playwright project's target); the release build (`pnpm build` without the flag) never installs it.

## Requirements

### Requirement 1 — Landing screen and samples

**User Story:** As a judge opening the hosted demo, I want one click to open a complete investigation of a real sample, with nothing between me and the map, so that I see source-backed rooms within seconds and can later confirm that the analysis is real.

#### Acceptance Criteria

1. WHEN the app loads at its base URL with no investigation in memory THEN THE SYSTEM SHALL render the landing screen (`src/components/Landing.tsx`) with the heading `HauntMap`, the one sentence `Find how the modules of a JavaScript or TypeScript project import each other: rooms are files, doors are imports, and a corridor that returns to its start is a dependency cycle.`, and two buttons in this DOM and Tab order: `Explore the manor` (primary), `Explore the annex`; the first Tab press from the document start SHALL land on `Explore the manor`.
2. THE SYSTEM SHALL show no splash, intro animation, modal or tutorial before the landing buttons are operable; the two buttons SHALL be enabled in the same render as the heading; no privacy sentence is shown because this build has no local-folder or GitHub route.
3. WHEN `Explore the manor` is activated THEN THE SYSTEM SHALL fetch `demo/manor/before/sources.json` relative to the app base in one request (`pnpm pack:samples`, owned by `analysis-core`, writes `{ files: [{ path, text }] }` there; `loadSample` builds the `SourceSet` with `rootLabel: "manor/before"`, `bytes` as the UTF-8 length of each text and `skipped: []`), run the analysis worker on it with the preset `static-value`, open the investigation screen on the Map view with the wing `src/orders` expanded and the camera fitted to that wing, and show the steps panel of Requirement 8; `Explore the annex` SHALL do the same with `demo/annex/sources.json`, the camera fitted to the whole overview and no steps panel.
4. WHEN the manor investigation has loaded THEN THE SYSTEM SHALL show `Modules (40)` in the Evidence view (under the heading `Evidence (static-value)`) and, after `Dependency loops` is opened under `static-value`, exactly one component with the members `src/notifications/receipt.ts`, `src/orders/checkout.ts`, `src/payments/charge.ts` (matrix row 13, as displayed); `tests/e2e/landing.spec.ts` reads every other manor fact it asserts from `public/demo/manor/before/expected.json` (fields: `modules`, `wings` keyed by the folder name under `src/` such as `orders`, `imports` without relation or occurrence IDs, `diagnostics`, `cycles` by preset, `receiptToCheckout`) rather than hardcoding it.
5. Withdrawn under the revision of 16 November 2026. The `intake` spec is not built, so the landing screen has no local-folder or GitHub button and no code of this spec calls an `intake` handoff.
6. IF a sample request fails (HTTP status other than 200, a network error or a JSON parse error) THEN THE SYSTEM SHALL keep the landing screen, show in the status region `The manor sample could not be loaded (<status or error name>). Reload the page.` (or `The annex sample …`), and leave focus on the activated button.
7. WHILE an investigation is open THE SYSTEM SHALL show `Restart demo` as the first toolbar control; WHEN it is activated THEN THE SYSTEM SHALL return to the landing screen, clear the investigation, the in-memory source text, the selection, the route filter, the expanded wings, the open panel and the steps state, destroy the scene, and keep only `localStorage["hauntmap.prefs.v1"]` in `localStorage`.
8. WHEN the hosted build is opened in two fresh browser profiles (no extensions, cleared storage) THEN THE SYSTEM SHALL reach the manor map from the landing screen with no account, API key, cookie banner or download (matrix row 19, sample portion); the check on a hosted build in two browsers needs a person and is left for the owner. `tests/e2e/landing.spec.ts` checks the same path headless in one fresh Chromium context with empty storage and states that it is not the hosted-build check.
9. WHEN `Explore the manor` is activated on the named laptop over broadband THEN THE SYSTEM SHALL emit `performance.mark("hauntmap:usable")` when the first room is drawn and the inspector shows the wing `src/orders`, within 3,000 ms of the activation; the figure is a target and the measurement is left for the owner (12.5).
10. IF the analysis worker rejects while a sample is being analyzed (`analysisClient.analyze` rejects, times out or is terminated) THEN THE SYSTEM SHALL keep the landing screen, show in the status region `The manor sample could not be analyzed (<message>). Reload the page.` (or `The annex sample …`), and leave focus on the activated button (`tests/ui/sample-loader.test.ts` with an injected rejecting client).

### Requirement 2 — The haunted map: rooms, wings, doors and corridors

**User Story:** As a developer, I want every drawn element to mean exactly one thing about the import graph, so that I can explain a dependency to a colleague from the screen without narration.

#### Acceptance Criteria

1. THE SYSTEM SHALL draw exactly one room per module of an expanded wing and one wing region per distinct wing of the investigation; every room SHALL have the same size (96 × 64 scene units) regardless of file size, import count or folder depth, so that no room looks more important than another.
2. THE SYSTEM SHALL draw one door per relation ID that is in the active preset, has `resolution: "local"` and whose importer and target rooms are both drawn; several occurrences of one relation ID SHALL produce one door; a relation outside the active preset SHALL produce no door while it stays listed in the Evidence view with its preset membership.
3. THE SYSTEM SHALL draw a relation with resolution `external`, `unresolved` or `unsupported` as a sealed doorway with a `?` glyph on the importer's room, one per relation ID, when the relation is in the active preset (the same shared preset rule as for a door, applied to the record's syntax and dependency kinds), and never as a room: the room count of a wing SHALL equal its module count for every investigation (matrix row 8, UI portion; `tests/ui/layout-engine.test.ts` on `tests/ui/fixtures/boundary.json`).
4. WHILE a cycle witness is the route filter THE SYSTEM SHALL draw its relations, in witness order, as one violet looping corridor whose last segment returns to the first room, with the step numbers `1`…`n` drawn at the doors; WHILE a trace path is the route filter THE SYSTEM SHALL draw a traveling light along the path with the step number at each door; under reduced motion (11.5) the light SHALL be a static marker at every step.
5. WHILE a route filter is active THE SYSTEM SHALL draw every room outside it subdued (fill `--room-subdued`, label `--room-subdued-ink`, no particles), describe the state as `Not in this traversal` in tooltips and the inspector, and SHALL never describe it as dead, unused or unreachable: `tests/ui/vocabulary.test.ts` fails if `dead code`, `unused`, `unreachable` or `orphan` appears in `src/scene/**` or `src/components/**`.
6. THE SYSTEM SHALL give every non-default element state a shape or text companion in addition to its color: `src/scene/styles.ts` exports `STATE_STYLES`, and `tests/ui/styles.test.ts` fails if any state other than `default` differs from `default` only in color (selected: 3-unit outline and the inspector heading; subdued: the `Not in this traversal` text; witness: step numbers; sealed: `?`; comparison states: the glyphs defined by `snapshot-comparison`).
7. THE SYSTEM SHALL compose the scene from six containers in this back-to-front order and with these names: `floor` (static floor and wing boundaries), `corridors` (unselected corridors and aggregated inter-wing corridors), `rooms` (room bodies and labels), `selected` (selected paths, doors and the witness corridor), `particles` (ambient particles, at most 40, none under reduced motion), `overlay` (focus halo and DOM overlay anchors); `tests/ui/layers.test.ts` asserts the order and names from `src/scene/layers.ts`.
8. THE SYSTEM SHALL draw no element whose size, color, glow or placement encodes vulnerability, runtime failure, test coverage, churn or maintenance risk; the drawn facts are exactly those of the plan's visual-language table (module, wing, relation, cycle witness, trace, boundary, comparison state, filter state), and `STATE_STYLES` has no key outside that list.
9. THE SYSTEM SHALL label each room with its file name (last path segment) clipped with `…` after 18 characters and each wing region with its wing path and module count (`src/orders · 7 modules`); the full module ID appears in the tooltip, the inspector and the Evidence view.

### Requirement 3 — Layout in a worker and wing expansion

**User Story:** As a developer with a large project, I want the overview grouped by folder with a deterministic layout computed off the main thread and a selected wing expanded to a readable number of rooms, so that a 1,000-module analysis stays navigable and nothing jumps between renders.

#### Acceptance Criteria

1. THE SYSTEM SHALL compute positions with dagre (MIT; the package name and exact version are pinned in task 1c, *verify* whether `dagre` or `@dagrejs/dagre` is pinned) through `src/scene/layout/engine.ts`, which runs only inside `src/workers/layout.worker.ts`; the revision of 16 November 2026 fixes dagre, so no ELK engine is built and `LayoutResult.engine` is `{ name: "dagre", version }` with the pinned version; the `LayoutEngine` interface stays so that an engine can be replaced later.
2. WHEN an investigation opens, or the expanded wings or the preset change THEN THE SYSTEM SHALL send exactly one layout request `{ requestId, revision, kind: "layout", payload }` through the layout client (`src/features/investigation/layoutClient.ts`; the analysis client of `src/workers/client.ts` speaks only `kind: "analyze"`) with `revision` incremented, and SHALL apply a `LayoutResult` only when its `revision` equals the current one; a result with an older revision SHALL be discarded without any visible change (`tests/ui/store.test.ts` delivers two results out of order); selection and route-filter changes SHALL send no layout request.
3. THE SYSTEM SHALL return, for deep-equal `LayoutRequest`s, deep-equal `LayoutResult`s with the same `layoutKey` (SHA-256 hex of the sorted module IDs, sorted drawn relation IDs, sorted boundary relation IDs, sorted expanded wings with their shown module IDs, preset, engine name and version), independent of the order of `modules` and `imports` in the investigation (`tests/ui/layout-key.test.ts` shuffles both arrays).
4. WHEN the overview is shown THEN THE SYSTEM SHALL draw one region per wing with its module count and one aggregated corridor per ordered wing pair that has at least one drawn relation, labelled with the relation count (`3 imports`), and SHALL draw individual doors only inside expanded wings and along the route filter.
5. WHEN a wing is expanded (by activating its region, by `Expand wing` in the inspector, or by a search result or selection inside it) THEN THE SYSTEM SHALL draw at most 80 rooms for it: all of its modules when it has at most 80, otherwise the 80 lexically smallest module IDs with the selected or searched module swapped into the last slot when it is not among them, plus one grouped room labelled `+<n> more modules` that opens the Evidence view filtered to that wing; the status region SHALL show `Showing 80 of <n> modules in <wing>. Search to bring another module into view, or use the Evidence view for the full list.` (`tests/ui/layout-cap.test.ts` on a generated 120-module wing).
6. WHEN a wing is expanded or collapsed THEN THE SYSTEM SHALL keep every wing's `rank` unchanged (ranks depend only on the wing graph; `tests/ui/layout-engine.test.ts` asserts the `rank` map deep-equal before and after), keep every wing box inside `bounds` without intersecting another wing box (asserted on every fixture and generated layout, P1), animate the move in 300 ms (or jump under reduced motion), keep the camera center in scene coordinates, and keep the selection and route filter.
7. IF the layout worker has not answered within 10,000 ms, or answers with an error THEN THE SYSTEM SHALL show in the status region `The map layout did not finish (<reason>). The Evidence view has the full investigation.` with a `Retry layout` button beside the Map view, switch to the Evidence view, and keep the investigation, selection and panels.
8. THE SYSTEM SHALL lay out a generated 200-module, 600-relation investigation within 1,000 ms inside the worker on the named laptop (this spec's share of the plan's 3-second parse-and-layout target, leaving 2,000 ms to the parser) and a generated 1,000-module overview within 3,000 ms, as targets whose measurement on a named laptop is left for the owner (12.5); `tests/ui/layout-engine.test.ts` checks the shape of both layouts and no timing.
9. THE SYSTEM SHALL accept `LayoutRequest.modules` and `LayoutRequest.relations` as plain lists rather than an `Investigation`, so that `snapshot-comparison` can lay out the union graph once; `store.actions.applyLayout(result)` SHALL accept an externally produced result, set `layout` and `layoutStatus: "idle"`, increment `layoutRevision` (so a store request in flight is discarded) and keep the camera center; `store.actions.replaceInvestigation(inv, sourceText, { keepLayout: true })` SHALL set `investigation` and `sourceText`, keep `layout`, `layoutRevision`, `layoutStatus`, `camera`, `expandedWings`, `preset`, `activeView` and `selection`, set `routeFilter` to `null` when any of its module or relation IDs is absent from `inv`, recompute an open `loops` panel with the same index and an open `whoImports` panel with the same origin (closing it when the origin is absent), and send no layout request; `store.actions.setLayoutRequestBuilder(builder | null)` SHALL make `openInvestigation`, `setPreset`, `expandWing`, `collapseWing` and `retryLayout` send the request the builder returns while one is set (the store's own request when the builder returns `null`); toggling a comparison side SHALL send no layout request from this spec's code (`tests/ui/store.test.ts` counts requests and covers each rule).

### Requirement 4 — Search, focus and camera

**User Story:** As a developer, I want to find a module by name, focus on its neighbourhood and move around the map with a mouse or a keyboard, so that reaching any room never depends on hunting through the drawing.

#### Acceptance Criteria

1. THE SYSTEM SHALL provide a search field labelled `Search modules` in the toolbar following the combobox pattern (`role="combobox"`, `aria-expanded`, `aria-controls`, `aria-activedescendant`, a `role="listbox"` of `role="option"` items); WHEN at least one character is present THEN THE SYSTEM SHALL list, within 200 ms, the modules whose ID contains the query case-insensitively, sorted by ID, at most 20 shown, with the text `<n> matches` when `n ≤ 20` and `20 of <n> matches` otherwise.
2. WHEN a result is chosen (Enter on the active option or a click) THEN THE SYSTEM SHALL select that module, expand its wing per 3.5, center the camera on its room at `max(zoom, 1)`, open the inspector on it and move focus to the inspector heading; the query SHALL stay in the field.
3. IF no module matches THEN THE SYSTEM SHALL show `No module matches "<query>".` in the listbox area and in the status region and leave the selection unchanged; the query string is rendered as text (6.6).
4. WHEN `Focus` is activated for the selected module (inspector button, or `F` while the map wrapper has focus) THEN THE SYSTEM SHALL set the route filter to that module, its direct importers and its direct imports under the active preset, subdue every other room, and show `Focused on <id>: <a> importers, <b> imports.` in the status region; WHEN `Clear selection` (toolbar button, or Escape while the map wrapper has focus) is activated THEN THE SYSTEM SHALL clear the selection and the route filter and restore every room.
5. THE SYSTEM SHALL pan by pointer drag and, while the map wrapper has focus, by ArrowUp, ArrowDown, ArrowLeft and ArrowRight (80 CSS px per press, 320 with Shift); SHALL zoom by wheel around the pointer, by `+`/`=` and `-` (factor 1.25) and by the toolbar buttons `Zoom in`, `Zoom out` and `Fit to view`; zoom SHALL stay within [0.25, 4]; `0` and `Fit to view` SHALL fit the drawn bounds with 32 px padding.
6. THE SYSTEM SHALL keep the camera (`x`, `y`, `zoom`), the minimap and the breadcrumb `<sourceLabel> › <wing>` unchanged across selection changes, route-filter changes and panel changes; WHEN a layout result moves rooms THEN THE SYSTEM SHALL keep the camera center in scene coordinates and re-fit only when `Fit to view` is activated.
7. THE SYSTEM SHALL show a minimap (160 × 100 CSS px, `aria-hidden="true"`, drawn from wing regions) with the viewport rectangle; WHEN it is clicked THEN THE SYSTEM SHALL move the camera center to that point; every navigation the minimap offers is also available through search and the Evidence view.
8. WHILE a scripted 2,000 ms pan-and-zoom runs over the manor's expanded `src/orders` wing plus the overview (the visible 80-room scene budget) on the named laptop THE SYSTEM SHALL render at least 100 frames (50 frames per second on average, target 50–60); a target whose measurement on a named laptop is left for the owner (12.5).

### Requirement 5 — Legend, tooltips and preset display

**User Story:** As a first-time user, I want the legend and every tooltip to name the real concept before the costume word and the active preset to sit beside every result, so that the haunted vocabulary never hides what the data means.

#### Acceptance Criteria

1. THE SYSTEM SHALL provide a `Legend` toggle button (`aria-expanded`) in the toolbar whose panel lists, in this order and wording: `Module — room`, `Folder — wing`, `Import or re-export — door and arrow`, `Dependency cycle — looping corridor`, `Unresolved or external import — sealed doorway with ?`, `Not in this traversal — subdued room`, `Dependency path — traveling light`; WHILE a comparison is active THE SYSTEM SHALL append the entries returned by the legend provider registered by `snapshot-comparison` (`Changed source — amber lamp`, `Removed in the newer snapshot — ghost outline`, `Added in the newer snapshot — green doorway`) and otherwise omit them.
2. WHEN a room, door, sealed doorway or wing is hovered, or receives keyboard focus through its Evidence-view or inspector item THEN THE SYSTEM SHALL show a tooltip anchored to the element's screen rectangle whose first line is the legend wording for that element and whose second line is the fact: room `<id> · <TypeScript|JavaScript|JSX|TSX> · <parsed|partially parsed|parse failed>`; door `<from> imports <to> · <syntaxKind> · <dependencyKind> · line <line of the first occurrence>`; sealed doorway `<from> → "<specifier>" · <resolution> · <reason>`; wing `<wing> · <n> modules`; the tooltip disappears on blur, on pointer leave and on Escape.
3. THE SYSTEM SHALL render legend, tooltip, inspector and evidence text with React text nodes only: no `dangerouslySetInnerHTML`, `innerHTML` or `insertAdjacentHTML` in `src/components/**`, `src/features/**` or `src/scene/**` (`tests/ui/no-html-injection.test.ts`), so IDs and specifiers containing `<`, `&` or quotes appear verbatim (matrix row 11).
4. THE SYSTEM SHALL show the active preset beside every result heading (`Dependency loops (static-value)`, `Who imports src/orders/checkout.ts (static-value)`), in the Evidence view heading (`Evidence (static-value)`) and in a toolbar `<select>` labelled `Relation preset` with the options `static-value`, `type-inclusive`, `dynamic-inclusive`; WHEN the preset changes THEN THE SYSTEM SHALL request a new layout (3.2) and recompute the open panel with the same origin or component index.
5. THE SYSTEM SHALL show in the legend panel's footer the text `Rooms show files and doors show imports found in the source. The map does not show runtime behaviour, test coverage or risk.`
6. THE SYSTEM SHALL persist whether the legend is open in `localStorage["hauntmap.prefs.v1"]` (`legendOpen`), default open, with every read and write wrapped so that a throwing or empty storage leaves the default.

### Requirement 6 — Inspector and evidence list share one selection

**User Story:** As a developer, I want the map, the inspector and the evidence list to always agree on what is selected and to show the exact source evidence, so that clicking a door is the same act as reading its import statement.

#### Acceptance Criteria

1. THE SYSTEM SHALL hold one `Selection` in the store; every selecting action (scene click, search choice, Evidence-view item, evidence-list step, inspector link, loops or who-imports item, steps panel) SHALL set it, and the scene highlight, the inspector and the evidence list SHALL reflect it within one render (`tests/ui/selection-roundtrip.test.tsx` with a fake scene asserts the scene's `setStyleState` argument, the inspector heading and the evidence list's `aria-current` row after each action).
2. WHEN a module is selected THEN the inspector (`<aside aria-label="Inspector">`) SHALL show the heading `<id>`, the lines `Wing: <wing>`, `Language: <label>`, `Parse status: ok|partial|failed`, a list `Imports (<n>)` of buttons `<to or "specifier"> · <syntaxKind> · <dependencyKind>` (one per relation ID under the active preset, sorted by relation ID), a list `Imported by (<m>)` likewise, the buttons `Focus`, `Who imports this?` and `Expand wing` or `Collapse wing`, and, when the module has diagnostics, a list `Diagnostics (<k>)` of `<code>: <message>`.
3. WHEN a relation is selected THEN the inspector SHALL show the heading `<from> imports <to>` (or `<from> → "<specifier>"` for a boundary), the lines `Syntax: import|re-export|dynamic-literal`, `Dependency: value|type|mixed`, `Resolution: local|external|unresolved|unsupported` with `Reason: <reason>` when present, `Preset: <in static-value|type-inclusive only|dynamic-inclusive only>` as reported by `src/analysis/graph`, and a list `Occurrences (<n>)` of buttons `line <line>, column <column>: <specifier>`; WHEN an occurrence is activated THEN THE SYSTEM SHALL show the source line with two lines before and after, one-based line numbers, as text; IF the investigation has no source text (live snapshot) THEN THE SYSTEM SHALL show `Source not included in this snapshot; evidence is path, line and specifier.`
4. THE SYSTEM SHALL render the evidence list (`<section aria-label="Evidence trail">`) as an ordered list of the route filter's relations, each item a button `Step <k>: <from> imports <to> (line <line>)` that selects the relation and centers the camera on its door, with `aria-current="step"` on the selected one; WHILE no route filter is active THE SYSTEM SHALL show `Select a loop or a module to build an evidence trail.`
5. THE SYSTEM SHALL provide the Evidence view (tab `Evidence`) listing, for the whole investigation: `Wings (<n>)` with module counts, `Modules (<n>)` sorted by ID with parse status, `Relations (<n>)` sorted by relation ID as `<from> imports <to|"specifier"> · <syntaxKind> · <dependencyKind> · <resolution> · <in preset|not in preset>`, and `Diagnostics (<n>)`; every item is a button that sets the same selection; `tests/ui/evidence-view.test.tsx` asserts that the set of module IDs and relation IDs rendered equals those of the investigation, so the view is a complete alternative to the canvas (matrix row 15 precondition).
6. WHEN `tests/ui/fixtures/escaped.json` (module `src/a&b.ts` importing `"./<img src=x onerror=alert(1)>"`, `resolution: "unresolved"`, `reason: "absent-file"`) is opened THEN the inspector, the Evidence view and the tooltip SHALL display both strings verbatim as text, `document.querySelector("img")` SHALL be null and no dialog SHALL open (matrix row 11, UI portion; the export portion is not built under the revision).
7. WHEN the inspector, the evidence list or the Evidence view selects something THEN the scene SHALL draw the focus halo on it (layer `overlay`) and center the camera per 4.2 (a relation whose door is not drawn, because an end room is not drawn, is centered on the importer's room, or on the importer's wing region when that wing is collapsed); WHEN the scene selects something THEN focus SHALL stay on the map wrapper and the inspector SHALL update without taking focus; `I` while the map wrapper has focus SHALL move focus to the inspector heading.
8. WHILE the renderer is unavailable (12.1) THE SYSTEM SHALL keep every behaviour of 6.2–6.6 working with the scene stubbed (the same unit tests run with `createScene` resolving `{ ok: false }`).

### Requirement 7 — Loops and who-imports as UI over analysis results

**User Story:** As a developer reviewing a change, I want to reveal one concrete dependency loop and see who reaches a module through imports, with direction and limits stated in prose, so that I inspect the right places without being told something will fail.

#### Acceptance Criteria

1. WHEN `Dependency loops` (toolbar) is activated THEN THE SYSTEM SHALL call `analysisApi.cycles(investigation, preset)` and show the panel `Dependency loops (<preset>)` with the count `<k> loops` and one button per cyclic component, in report order, labelled `<n> modules: <member 1>, <member 2>, …` (`Self-import: <member>` for a size-one component); for the manor under `static-value` the panel SHALL list exactly `3 modules: src/notifications/receipt.ts, src/orders/checkout.ts, src/payments/charge.ts`.
2. WHEN a component is chosen THEN THE SYSTEM SHALL set the route filter to its witness (modules and relation IDs in witness order), draw the looping corridor (2.4), fill the evidence trail with the witness relations, select the first witness relation, center the camera on its door and keep focus on the chosen button; THE SYSTEM SHALL never enumerate all simple cycles and provides no `Next witness` control in this release.
3. WHILE the active preset is `type-inclusive` THE SYSTEM SHALL show under the loops heading `This preset includes type-only relations, which the static-value preset leaves out; a loop that exists only here is not a runtime import cycle.`; WHILE it is `dynamic-inclusive` THE SYSTEM SHALL show `This preset also includes literal dynamic imports.` (matrix rows 5 and 6, UI portion).
4. WHEN `Who imports this?` is activated for the selected module THEN THE SYSTEM SHALL call `analysisApi.trace(investigation, id, "imported-by", preset)` and show the panel `Who imports <id> (<preset>)` with `Direct importers (<a>)` and `Indirect (<b>)` as separate lists sorted by ID (`direct` and `indirect` of the `TraceResult`), each item `<module> · <distance> steps`, and the sentence `These modules reach <id> through imports under this preset. They are places to inspect, not modules that will fail.`
5. WHEN a result module is chosen THEN THE SYSTEM SHALL build the shortest path from the chosen module to the origin by following `predecessor` from the chosen module, set the route filter to that path (modules and the relation ID of each step), fill the evidence trail with it, draw the traveling light from the chosen module to the origin, select the first step, and show the prose `<chosen> reaches <origin> in <d> steps: <chosen> imports <m1>, <m1> imports <m2>, …, <mk> imports <origin>.`
6. WHEN the panel for the manor shows `Who imports src/orders/checkout.ts` under `static-value` THEN `src/notifications/receipt.ts` SHALL appear under `Direct importers` (the plan's `receipt.ts → checkout.ts` relation) and the distances and counts SHALL equal those of a breadth-first search that `tests/e2e/loops-trace.spec.ts` writes itself over the `imports` list of `expected.json` (that file has no trace field); by hand, `Direct importers (1)` is `src/notifications/receipt.ts` at 1 step and `Indirect (1)` is `src/payments/charge.ts` at 2 steps.
7. THE SYSTEM SHALL use only the verbs `imports`, `imported by` and `reaches` for graph relations in both panels; `tests/ui/vocabulary.test.ts` fails if `breaks`, `fails`, `broken`, `dead`, `unused` or `risk` appears in `src/components/LoopsPanel.tsx` or `src/components/WhoImportsPanel.tsx`.
8. IF `analysisApi.cycles` or `analysisApi.trace` throws THEN THE SYSTEM SHALL show in the panel `Could not compute <loops|importers> for this preset: <error message>.`, keep the previous route filter and selection, and log the error to the console without the source label or any path (no telemetry exists).

### Requirement 8 — Three optional investigation steps and restart

**User Story:** As a judge, I want three optional steps that walk me through following a dependency, revealing a loop and comparing revisions, each skippable and none blocking, so that I understand the product in under two minutes without a tutorial gate.

#### Acceptance Criteria

1. WHEN the manor opens from `Explore the manor` THEN THE SYSTEM SHALL show a panel headed `Investigate the manor` (`<section aria-label="Investigation steps">`, not modal, no focus trap, closable with `Close`) with `<done> of <n> steps` and the steps, each with a title, one instruction and the buttons `Do it` and `Skip`: 1 `Follow a dependency` — `Select src/orders/checkout.ts and open one of its doors.`; 2 `Reveal a loop` — `Open Dependency loops and choose the 3-module loop.`; 3 `Compare revisions` — `Load the revised manor and watch which door disappears.`
2. WHEN `Do it` is activated on step 1 THEN THE SYSTEM SHALL select `src/orders/checkout.ts`, center the camera on it and move focus to the first `Imports` button of the inspector; the step becomes `Done` when any relation with `from: "src/orders/checkout.ts"` is selected by any means.
3. WHEN `Do it` is activated on step 2 THEN THE SYSTEM SHALL open the loops panel and move focus to its first component button; the step becomes `Done` when a witness route filter is active.
4. WHEN `Do it` is activated on step 3 THEN THE SYSTEM SHALL call the `compare` handoff registered by `snapshot-comparison` through `callCompareHandoff` (`src/features/investigation/handoffs.ts`) with `{ before: <current investigation>, after: { sample: "manor/after" }, layoutKey: state.layout?.layoutKey ?? null }`; IF no `compare` handoff is registered THEN step 3 SHALL not be rendered and the heading SHALL read `<done> of 2 steps`; the step becomes `Done` when the handoff resolves and stays `To do` when it rejects (the handoff wrote its own message; no second one is written).
5. THE SYSTEM SHALL let the steps be done in any order; `Skip` marks a step `Skipped`; a step's status is shown as text (`Done`, `Skipped`, `To do`) next to its title; the state lives in memory for the session and is reset by `Restart demo` (1.7).
6. THE SYSTEM SHALL not show the steps panel for the annex or a live snapshot; the steps are a property of the manor demo only.
7. WHEN the steps panel is closed or every step is done or skipped THEN THE SYSTEM SHALL keep a `Show steps` toolbar button that reopens it with the same state; focus returns to that button when the panel closes.

### Requirement 9 — Hit targets and rendering budget

**User Story:** As a user with a trackpad, I want every door and room to be clickable where it looks clickable and the map to stay smooth on an ordinary laptop, so that the illustration never gets in the way of the investigation.

#### Acceptance Criteria

1. THE SYSTEM SHALL compute every door's and sealed doorway's hit target as an axis-aligned rectangle in scene units from the `LayoutResult` (`src/scene/hitTest.ts`), independent of the drawn art, at least 24 × 24 scene units (24 CSS px at zoom 1); two targets on the same room SHALL not overlap; `hitTest(point)` SHALL return the topmost target with the priority door, sealed doorway, grouped room, room, wing; `tests/ui/hit-test.test.ts` checks these on the manor layout and on generated layouts (P4).
2. WHEN a pointer click lands inside a door's hit rectangle THEN THE SYSTEM SHALL select that relation; inside a room but no door, the module; inside a wing region but no room, the wing; elsewhere, nothing; `tests/e2e/map-scene.spec.ts` clicks the center of `scene.screenRectOf({ kind: "door", id })` for every door of the manor's `src/orders` wing and asserts the inspector heading each time.
3. THE SYSTEM SHALL generate each room, wing, door, sealed-doorway and corridor texture once per (element kind, state) and reuse it (`src/scene/textures.ts`, cache key `<kind>:<state>`); after drawing the manor with one selection and one witness, `scene.debug().textureCount` SHALL be at most 24, and loading three investigations in a row SHALL not raise it above the single-load value.
4. THE SYSTEM SHALL skip rendering a room whose bounds lie fully outside the viewport plus a 100 px margin (`scene.debug().visibleRooms` equals the number of rooms intersecting that area), and SHALL pause the ticker while `document.visibilityState` is `hidden` or while the map container has zero intersection with the viewport (IntersectionObserver) and resume on return (`scene.debug().tickerRunning`).
5. THE SYSTEM SHALL animate at most the selection transition (≤ 300 ms), the wing move of 3.6, the traveling light (1,200 ms per step, looping), the particles layer (≤ 40 sprites) and the comparison transition owned by `snapshot-comparison`; THE SYSTEM SHALL apply no full-screen filter, displacement or blur and no continuous animation to rooms outside the route filter; one second after the last interaction with nothing selected, `scene.debug().activeTweens` SHALL be 0.
6. WHEN a DOM control is used (search keystroke, Evidence-view item, panel open, tab switch, `Focus`, `Clear selection`) on the named laptop THEN THE SYSTEM SHALL commit the resulting DOM update within 200 ms (p95 over 20 scripted interactions, `performance.mark` pairs around dispatch and commit); a target whose measurement on a named laptop is left for the owner (12.5).
7. WHEN `Restart demo` is activated or the investigation screen unmounts THEN THE SYSTEM SHALL call `scene.destroy()`, which destroys cached textures, removes the resize, visibility, intersection and context listeners and stops the ticker; `tests/e2e/map-scene.spec.ts` asserts `scene.debug()` throws `Scene destroyed` afterwards and that a second `Explore the manor` creates a fresh scene.

### Requirement 12 — Renderer fallback, context loss, measured performance and review evidence

**User Story:** As the owner judging this build, I want the map to degrade to the evidence view when graphics fail, every performance figure to wait for a recorded run on named hardware, and every finished task to carry a log row, so that nothing about the interface is claimed without evidence.

#### Acceptance Criteria

1. IF the scene adapter cannot initialize (PixiJS initialization rejects, no WebGL context, or the development-build query `?renderer=off`) THEN THE SYSTEM SHALL show inside the Map view the banner `The illustrated map could not start in this browser. The Evidence view has every room, door and corridor as lists.` with the buttons `Retry map` and `Open Evidence view`, switch to the Evidence view, keep the investigation, selection, panels and steps, move focus to `Retry map`, and SHALL not reach the error boundary (matrix row 15).
2. WHEN `Retry map` is activated THEN THE SYSTEM SHALL run initialization again; IF it succeeds THEN the scene draws the current layout with the current selection and camera; IF it fails THEN the banner stays; in both cases the investigation, selection and route filter SHALL be deep-equal before and after (`tests/e2e/renderer-fallback.spec.ts` toggles the development hook `window.__hauntmap.forceRendererFailure(boolean)`).
3. WHEN the canvas fires the standard WebGL event `webglcontextlost` (simulated in e2e through the `WEBGL_lose_context` extension, or, when headless Chromium does not expose it, by dispatching the same event on the canvas, which the adapter listens to either way) THEN THE SYSTEM SHALL show `The map lost its graphics context. Retrying…` in the banner area, stop the ticker and keep the DOM interactive; WHEN `webglcontextrestored` fires THEN THE SYSTEM SHALL rebuild the texture cache and redraw within 1,000 ms; IF no restore arrives within 5,000 ms THEN THE SYSTEM SHALL show the banner of 12.1; the investigation is never cleared.
4. THE SYSTEM SHALL wrap the investigation screen in an error boundary (`src/components/ErrorBoundary.tsx`) that, on a render error, shows `Something went wrong drawing the map. Your investigation is still loaded.` with `Reload view` (re-mounts the screen with the same store) and logs only the error name and stack to the console; no repository name, source label or file path is written to any storage or network endpoint (no telemetry exists in this build).
5. Not built under the revision of 16 November 2026, because a performance row needs a named laptop and a person. WHEN a task of this spec is finished THEN Kiro SHALL append one row for it to `docs/kiro-log.md` the same day (task number, files or commit, `pnpm verify` and, where the task names it, `pnpm verify:e2e` results, the boundary tests of 5.3, 10.6 and `tests/analysis-boundary.test.ts` where they ran, what failed and was changed, credits used); there are no separate review rows, no outside reviewer and no credit cap beyond the owner's; a task that was not built (task 0, the performance part of task 14) is listed as not built in the last row.
